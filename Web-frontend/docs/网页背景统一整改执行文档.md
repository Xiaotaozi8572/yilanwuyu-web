# 网页背景统一整改执行文档

> 适用项目：`挑战杯前端`（Vue 3 + Vite，C919 / J20 / Y20 / Z20 四机型共 35 个路由页面）
> 整改范围：**仅限背景（background）相关 CSS 属性**，不涉及任何内容与布局改动
> 文档版本：v2.9（2026-08-26）——第二十四章：后端 LLM 供应商由 DeepSeek 切换为 Qwen（V2 目录联调准备），见 24.x

---

## 一、整改目标（三条硬性要求）

| 编号 | 要求 | 判定方式 |
|---|---|---|
| G1 | 网页背景占满整个页面 | 任意窗口比例下，背景图/背景色铺满全屏，无露底色条 |
| G2 | 禁止出现颜色分层 | 舞台内外、页面上下、左右边缘均不得出现肉眼可辨的色块分界 |
| G3 | 无背景图的页面统一使用一个颜色背景 | 所有无背景图页面的底色一律为 `var(--color-bg)` |

**总约束**：整改期间每一个网页的**内容和布局必须保持不变**（文字、按钮、热点、面板、3D 模型、iframe 的位置与尺寸一律不动）。

## 二、统一基准

### 2.1 唯一背景色

```css
var(--color-bg);   /* = #0a0c10，定义于 src/style.css :root，SceneShell 已在使用 */
```

- 该变量已存在，**禁止修改其定义值**。
- 整改后所有页面底色（含舞台外露区域）均为这一个颜色。

### 2.2 判定规则（执行时逐条对照）

| 规则 | 内容 | 处理 |
|---|---|---|
| R1 | 页面根容器的底色层 | 统一替换为 `var(--color-bg)` |
| R2 | 双色/多色底色渐变（如 `#000 → #020303`、`#151820 → #0a0c10`，肉眼可辨的上下色差） | 移除渐变层，替换为 `var(--color-bg)` 纯色 |
| R3 | 氛围光晕（`radial-gradient` 带 `transparent` 渐隐）、暗角、网格纹理、边缘压暗等装饰层 | **保留不动**（不属于颜色分层，是统一底色上的质感效果） |
| R4 | 背景图 | 容器必须铺满舞台（`width: 100%`），图片 `object-fit: cover` / `background-size: cover` 保持不变 |
| R5 | 内容布局属性（`position`、`inset`、`margin`、`padding`、`flex/grid`、字号、尺寸、`z-index`） | **一律禁改**，唯一例外见阶段 2 的宽度扩展 |

### 2.3 背景图裁切说明（预期效果，非缺陷）

实测图片尺寸：

| 图片 | 尺寸 | 宽高比 | 扩展满屏后 |
|---|---|---|---|
| aircraft-selection-gallery.jpg | 1672×941 | 1.777（≈16:9） | 完美铺满，无裁切 |
| core-wind-tunnel.png | 1555×1011 | 1.538 | cover 自动裁切上下约 13% |
| quiz-training-hangar.png | 1555×1012 | 1.537 | cover 自动裁切上下约 13% |
| explode-engineering-lab.webp / classroom-aviation-studio.webp | — | — | cover 自动适配 |

图层从 86.54% 扩展到 100% 后，非 16:9 图片会被 `cover` 轻微裁切上下边缘，这是「背景占满整个页面」的**预期结果**。禁止为避免裁切而改用 `contain`（会留白）或缩回宽度。

## 三、现状问题诊断

### 问题 1：视口与舞台双色分层（最严重）

- `src/style.css` L200：`#app { background: #020305; }`
- `src/App.vue` L28：`#app-root { background: #020305; }`
- `#app-stage`（16:9 舞台）背景为 `var(--color-bg)` = `#0a0c10`

**后果**：窗口比例非 16:9 时，舞台内是 `#0a0c10`、舞台外露出 `#020305`，四周出现一圈明显色差。

### 问题 2：背景图层不满屏（左右露底色条）

SceneShell / Z20SceneShell 中：

```css
.image-layer          { width: 86.53846154%; }  /* 背景图片层，左右各露 6.73% */
.scene-background-plane { width: 86.53846154%; }  /* 背景插槽层（风洞图、测验图都在此层内），同样不满屏 */
```

ExplodeViewPage（4 个机型同构）中：

```css
.environment { width: 86.53846154%; }  /* 工程实验室环境图，居中且不满屏 */
```

**后果**：使用 SceneShell 的页面（Intro、CoreInteraction、Quiz、Result 共 13 个页面）背景图只占中间 86.54% 宽，两侧露出底色，形成「图—色—图」三层观感；爆炸拆解页同理。

## 六、禁止行为清单（禁令）

执行整改时，以下行为**一律禁止**：

### 布局与内容类

1. **禁止修改任何布局属性**：`position`、`inset`、`top/left/right/bottom`、`margin`、`padding`、`display`、`flex*`、`grid*`、`transform`、字号、行高、宽高（唯一例外：本方案明确列出的 `width: 86.53846154% → 100%` 共 6 处）。
2. **禁止触碰 `.scene-design-plane`**（两个 SceneShell 组件内）：它是全部页面内容的坐标基准，改动会导致所有热点、按钮整体错位。
3. **禁止删除、移动、修改任何页面内容元素**：文字、标题、按钮、热点、面板、图片引用、3D 模型、iframe、组件 import 均不得改动。
4. **禁止修改 `z-index`、动画（`animation`）、过渡（`transition`）**。

### 背景类

5. **禁止引入任何新的背景色值**：所有底色只能写 `var(--color-bg)`，不得新增十六进制色值，也不得硬编码 `#0a0c10`。
6. **禁止修改 `--color-bg` 变量的定义值**（`#0a0c10`）。
7. **禁止删除氛围光晕、暗角、网格纹理、边缘压暗等装饰层**：只允许移除本方案明确列出的「双色底色渐变」层。
8. **禁止为避免图片裁切而改用 `object-fit: contain`、`background-size: contain` 或缩回图层宽度**：cover 裁切是预期效果。
9. **禁止改动背景图的 `object-fit: cover` / `background-size: cover` / `background-position: center`**。

### 流程类

10. **禁止在未备份的情况下开始修改**（项目非 git 管理，备份是唯一回滚手段）。
11. **禁止改动 `src/` 之外的任何文件**：`dist/`、`dist-old-*/`、`public/`、`node_modules/`、后端目录一律不碰。
12. **禁止修改 JS 逻辑**：路由（`router/index.js`）、`main.js`、服务层、工具函数（`utils/assets.js` 等）不在本次范围。
13. **禁止修改 `FerrofluidBackground.vue`**（未被引用，保持原样）。
14. **禁止一次性全部改完才验证**：必须按「阶段 1 → 验证 → 阶段 2 → 验证 → …」的节奏推进，每个阶段验证通过再进入下一阶段。
15. **禁止顺手重构、格式化、优化与本任务无关的代码**：只改方案列出的行，不做任何额外「清理」。

## 十一、背景铺满整个视口（v1.2，2026-08-22）

### 11.1 需求

用户反馈：窗口比例非 16:9（如超宽屏）时，16:9 舞台两侧露出的纯色底与中间背景图形成明显色差（「两边的颜色和中间的背景不一样」）。要求**中间的背景占满整个网页，视觉上没有黑色的两边**。

### 11.2 技术要点（为什么必须用 Teleport）

- `#app-stage` 声明了 `container-type: size`（等价于 `contain: size layout style`），其中 **layout containment 会使该元素成为其 fixed 定位后代的包含块**。因此舞台内任何 `position: fixed` 元素的实际定位基准是 16:9 舞台本身，无法突破到视口。
- `.scene-frame` / 各页面根容器均有 `overflow: hidden`，absolute 溢出方案同样被裁切。
- 结论：背景层必须**脱离 #app-stage 的子树**。Vue 3 的 `<Teleport to="body">` 把背景层传送到 body 下，body 无 containment / transform / overflow 限制，`position: fixed; inset: 0` 即可真正铺满视口。

### 11.3 统一层级契约

```
body
├── 视口背景层（Teleport 传送，position: fixed; inset: 0; z-index: 0）
└── #app-root
    └── #app-stage（z-index: 1，舞台内容整体在视口背景层之上）
```

- 视口背景层必须 `pointer-events: none`，不遮挡交互。
- `#app-stage` 的 `z-index: 1` 是层级契约的关键（`src/App.vue` 已加），缺少它舞台内容会被后挂载的背景层遮盖。

### 11.4 修改清单（12 个文件）

| 文件 | 修改内容 |
|---|---|
| `src/App.vue` | `#app-stage` 增加 `z-index: 1` |

| `src/components/Z20SceneShell.vue` | 同上（覆盖 J20/Y20/Z20 的交互/测验/结果页） |
| `src/views/AircraftSelectPage.vue` | 新增 Teleport 视口层 `.select-viewport-bg`（背景图 + 遮罩从 `.select-frame` 迁移过去），`.select-frame` 移除 `background-image` 与 `::before` 遮罩 |

## 十二、背景双副本渲染：修复 Teleport 导致的 screen 混合失效（v1.3，2026-08-22）

### 12.1 回归现象

第十一章方案上线后，用户反馈核心交互页「中间变成黑色」：页面中央显示的是纯底色 `#0a0c10`，而舞台外（16:9 之外的视口区域）反而显示背景图——**与预期完全相反**。

像素实测（飞机与时间轴之间的纯背景区域）：标准差仅 **0.4**（min=14 / max=16），即一片平底色，无任何背景纹理。

### 12.2 根因分析

SceneShell 系页面的视觉是**混合叠加**出来的：

- `.image-layer`（UI 设计图 `c919按钮展开.jpg`，黑底 + 按钮/时间轴/标签图形）声明了 `mix-blend-mode: screen`；
- screen 混合使 UI 图的黑色部分「透明」，透出其下方背景插槽层（风洞图）；
- 两者**必须在同一层叠上下文**内，混合才能生效。

第十一章把 `.scene-background-plane` Teleport 到 body 后，背景层脱离了 `.scene-frame` 子树。而 CSS 混合的作用域被限制在**最近的层叠上下文祖先**内：

- `.scene-frame` 有 `isolation: isolate`（本来就是为包含 screen 混合而设）；
- `#app-stage` 有 `container-type: size`（等价 `contain: size layout style`，layout containment 会创建层叠上下文）。

两道隔离把 UI 图层与 body 级背景层彻底隔开——UI 图的黑色区域 screen 混合的底图变成了舞台底色，于是「中间变黑」；风洞背景图虽然铺满视口，却被不透明的 `#app-stage` 背景盖住，只在舞台外露出。

### 12.3 修复方案：背景插槽双副本渲染

背景插槽（`<slot name="background" />`）渲染两次，两个副本均为**视口尺寸**、内容逐像素一致：

```
body
├── .scene-background-plane（Teleport 副本，fixed inset 0，z-index 0）→ 铺满视口
└── #app-stage（z-index 1，不透明背景盖住 Teleport 副本的舞台内部分）
    └── .scene-frame（overflow: hidden 裁切，isolation: isolate）
        ├── .scene-inner-background（新增内部副本：absolute，100vw×100vh，
        │    left/top 50% + translate(-50%,-50%) 居中于舞台中心=视口中心，z-index 0）
        │    → 在 frame 内提供 screen 混合底图，恢复原有叠加效果
        ├── .image-layer（screen 混合，底图=内部副本 ✓）
        └── ...
```

无接缝的原理：`.scene-frame` 在视口中居中（app-root / app-stage / scene-shell 三层均 grid 居中），内部副本以舞台中心为圆心、以视口为尺寸铺开，`cover` 裁切结果与 Teleport 副本逐像素一致；frame 的 `overflow: hidden` 在舞台边界裁切内部副本，Teleport 副本在同一位置无缝续接。

覆盖页面：四机型核心交互页 ×4（`image-blend-mode="screen"`）+ 四机型测验页 ×4 + 两 Shell 内部 vignette 的 screen 混合。使用 Shell 但无背景插槽的页面（如首页）双副本为空容器，无副作用。

结构验证：`coreBgCount = 2`，两副本 rect 一致（均视口尺寸）；`imageLayerBlend = screen`；内部副本父级为 `scene-frame`、尺寸等于视口。

## 十三、切换过渡不同步：透明夹层方案（v1.5，2026-08-22）

### 13.1 回归现象

用户反馈：页面切换时，16:9 舞台左右边界出现两条竖线，**线两侧的画面不是同时切换，而是有先后顺序**（一侧先变、另一侧后变）。

### 13.2 根因分析

路由切换用 `<transition name="fade" mode="out-in">`（App.vue）：`opacity 0.45s + scale(0.992)`，**过渡类只加在 `.app-route` 根元素上**。由此产生时间差：

- 舞台**内**：内部背景副本是 `.app-route` 的后代，跟着一起淡出/淡入；淡出时露出的是 `#app-stage` / `.scene-frame` 等层的**不透明底色**（#0a0c10）——舞台内先变暗；
- 舞台**外**：Teleport 到 body 的视口副本**不参与过渡**（不在 `.app-route` 子树内），保持满透明度直到组件卸载那一刻才瞬间切换——舞台外后变。

于是切换全程，舞台边界两侧处于不同状态（一侧暗底色、一侧旧背景图），边界"裂开"成两条竖线。

### 13.3 修复方案：透明夹层

把夹在「渐变内容」与「Teleport 副本」之间的**所有不透明底色改为透明**。渐变时舞台内露出的不再是底色，而是与舞台外**同一个** Teleport 元素：

```
body
└── .scene-background-plane（Teleport 副本，fixed，opacity 恒为 1，全程静止）← 舞台内外共用的唯一可见背景
└── #app-stage（transparent）→ .scene-shell（transparent）→ .scene-frame（transparent）
    └── .app-route（唯一参与 fade 的层）
        ├── .scene-inner-background（内部副本，随内容一起渐变）
        └── 页面内容
```

数学上闭环：设过渡中内容透明度为 α，舞台内 = Teleport 副本 + 内部副本(α)×叠加 + 内容(α)。由于内部副本与 Teleport 副本**逐像素相同**，`副本(α) 叠加在副本上 ≡ 副本`（不可见），所以舞台内 = Teleport 副本 + 渐变中的内容，舞台外 = Teleport 副本——**边界两侧由同一个元素渲染，必然连续**。切换全程视觉上只有内容在渐变，背景纹丝不动；新旧背景在组件替换的那一帧全视口同步切换。

## 十四、时间轴入场动画会话级控制：修复切换翻转时的遮罩矩形（v1.7，2026-08-22）

### 14.1 回归现象

用户反馈：点击右侧菜单「知识巩固」等按钮、页面翻转（路由淡入淡出过渡）时，核心交互页底部时间轴区域出现异常画面——时间轴里程碑卡片被**深色半透明矩形**（`.timeline-item-mask`）覆盖、进度滑块上悬浮**发光箭头**（`.timeline-runner`），部分机型还叠加**青色描边高亮框**（`.timeline-hit::after`）。C919 / J20 / Y20 / Z20 四个机型交互页均存在（用户反馈「有许多也是这样」）。

### 14.2 根因分析

核心交互页底部时间轴带有一套**约 7 秒的一次性入场动画**：

| 元素 | 动画 | 时长/延迟 | 中间态 |
|---|---|---|---|
| `.timeline-item-mask` ×6 | `timelineItemReveal` | 0.42s，延迟 0.33s + i×1.18s | 深色矩形盖住里程碑卡片，依次消失（最后一块到 ~6.6s 才消失） |
| `.timeline-runner::before` | `timelineProgress` | 6.6s | 发光进度条从左向右生长 |
| `.timeline-runner::after` | `timelineArrowTravel` | 6.6s | 白色菱形箭头沿线滑动 |
| `.timeline-hit` ×6 | `timelineHit` | 0.72s，延迟 0.33s + i×1.18s | 白圈 + 青色描边高亮框闪现 |

问题在于动画**每次组件挂载都重播**，且中间态在两种场景下暴露：

1. **离开页面时**：动画播放期间（挂载后 ~7 秒内）点击「知识巩固」等菜单按钮，0.45 秒淡出过渡期间离开中的页面仍以动画中间态可见——用户截图中的「灰色矩形 + 滑块箭头」正是此状态；
2. **返回页面时**：从测验页等返回交互页，组件重新挂载，动画从头重播，时间轴再次长时间处于「遮罩盖住」的中间态。

### 14.3 修复方案：每机型每会话只播放一次 + 离开页面立即收尾

三个环节配套（缺一不可）：

**① 会话级播放标记（sessionStorage）**——重访直接呈现完成态：

```js
const skipTimelineIntro = ref(false)
const timelineIntroKey = 'c919:timeline-intro-played'   // 各机型独立 key

onMounted(() => {
  if (sessionStorage.getItem(timelineIntroKey)) {
    skipTimelineIntro.value = true       // 重访：跳过动画
  } else {
    sessionStorage.setItem(timelineIntroKey, 'true')   // 首访：播放设计内入场动画
  }
})
```

**② 路由离开立即收尾（onBeforeRouteLeave）**——淡出过渡期间不再显示中间态：

```js
onBeforeRouteLeave(() => {
  skipTimelineIntro.value = true         // 点击菜单按钮的瞬间，动画元素立即隐藏
})
```

该钩子在 fade 过渡开始**之前**执行，离开中的页面时间轴瞬间跳到终态，0.45 秒淡出期间画面干净。

**③ skip-intro 终态样式**——强制全部动画元素不可见：

```css
.timeline-stage.skip-intro .timeline-item-mask {
  animation: none;
  opacity: 0;
  visibility: hidden;
}
.timeline-stage.skip-intro .timeline-runner::before,
.timeline-stage.skip-intro .timeline-runner::after {
  animation: none;
  opacity: 0;
}
.timeline-stage.skip-intro .timeline-hit {
  animation: none;
  opacity: 0;
}
```

模板绑定：`<section class="timeline-stage" :class="{ 'skip-intro': skipTimelineIntro }">`。

修复后的行为：**首次访问**播放设计内入场动画（保留原设计）；**重访**时间轴直接呈现完成态；**任何时刻离开页面**（含动画播放中点击菜单）动画元素立即隐藏，切换过渡全程无遮罩矩形。

## 十五、首页导入视频进入即播放（v1.8，2026-08-23）

### 15.1 需求

用户要求：直接打开网站时，导入页视频就处于播放状态，不再出现播放按钮。

### 15.2 原行为与根因

`src/views/IntroPage.vue` 原逻辑：`onMounted` 调用 `startVideo()` 尝试 `video.play()`；失败（`isPlaying` 保持 false）时显示播放按钮遮罩 `.play-overlay`。

ffprobe 实测导入视频（`c919-assets/导入页/026771503d2b485fca0e3c50e928cc84.mp4`）含 **AAC 音轨**——浏览器自动播放策略拦截「带声音的自动播放」，`play()` 被拒绝，于是每个新会话首次进入网站都会看到播放按钮。

### 15.3 修复方案

`startVideo()` 改为两级尝试（修改仅此一处逻辑 + 删除遮罩死代码）：

```js
async function startVideo() {
  const video = videoRef.value
  if (!video) return

  try {
    await video.play()          // ① 优先有声自动播放（浏览器放行时直接带声播放）
    isPlaying.value = true
    return
  } catch {
    // 浏览器自动播放策略拦截带声音的视频，降级为静音播放
  }

  video.muted = true
  try {
    await video.play()          // ② 静音自动播放（各浏览器策略均放行）
    isPlaying.value = true
  } catch {
    isPlaying.value = false     // 极端设置（如全局禁用自动播放）下点击仍可播放
  }
}
```

同时删除模板中的 `.play-overlay` 播放按钮及其全部样式（死代码）。

行为结果：**进入网站视频立即播放**（浏览器允许则有声，否则静音）；播放结束自动进入机型选择页；点击页面任意处跳过；点击视频本体暂停/继续；Enter/Space 键触发播放——以上交互全部保持原状。

## 十六、模拟驾驶页全景铺满 + 返回键圆形修复（v2.0，2026-08-23）

### 16.1 需求

用户反馈两点：① 模拟驾驶页也要「全景图」效果，左右两边不要有黑色区域；② 模拟驾驶的返回键不是圆形，请修改。适用于 C919 / J20 / Y20 / Z20 四个机型。

### 16.2 根因分析

**① 左右黑边**：四个模拟驾驶页（CockpitPage.vue / J20CockpitPage.vue / Y20CockpitPage.vue / Z20CockpitPage.vue）的 iframe 原来直接放在舞台内（`.sim-shell` 全尺寸）。舞台 `#app-stage` 是 16:9 短边适配（`width: min(100vw, calc(100vh * 16/9))`）且设置了 `container-type: size`（contain 会把 fixed 定位困在舞台内），窗口比 16:9 更宽时 iframe 只占舞台宽度，两侧露出 `var(--color-bg)` 黑底——与其他页面整改前的「左右黑边」同源。

**② 返回键变椭圆**：四个模拟器（`public/c919-sim` 等）内 `.back-btn` 容器为 `width: 4.808%; height: 8.547%`（相对视口）。原 16:9 iframe 内两者恰好相等（8.547% × 9/16 = 4.808%），`::after` 的 `border-radius: 999px` 呈正圆；iframe 铺满整个视口后，非 16:9 窗口下宽高不等，圆形被拉成椭圆。

### 16.3 修复方案

**① iframe Teleport 全屏化**（四个 Cockpit 页面，以 C919 为例；Y20 沿用 `y20-` 前缀类名）：

```vue
<main class="sim-shell">
  <Teleport to="body">
    <div class="sim-viewport" :class="{ leaving: viewportLeaving }">
      <iframe class="sim-frame" :src="simUrl" ... />
    </div>
  </Teleport>
</main>
```

```css
.sim-viewport {
  position: fixed;
  inset: 0;
  z-index: 2;          /* 高于 #app-stage（z-index 1），iframe 是页面唯一内容 */
  overflow: hidden;
  background: #060a12; /* 与四个模拟器 body 底色一致，避免加载期白闪 */
  animation: simViewportIn 0.45s var(--ease-smooth, cubic-bezier(0.22, 0.75, 0.18, 1));
}
.sim-viewport.leaving { opacity: 0; transition: opacity 0.45s var(--ease-smooth, ...); }
```

- 脚本新增 `onBeforeRouteLeave(() => { viewportLeaving.value = true })`：离开时容器淡出与路由 fade（0.45s）同步，避免 Teleport 元素不参与路由过渡导致的「覆盖到最后一刻突然消失」。
- iframe 铺满视口后，模拟器内 three.js 按视口真实宽高渲染（`renderer.setSize(innerWidth, innerHeight)`），驾驶舱场景自然延伸到整个窗口——即「全景」效果；模拟器内 HUD（摇杆/踏板/姿态仪）为百分比定位，自适应无碍。
- 舞台内 `.sim-shell` 保留（被 iframe 覆盖，作为过渡底色）。

**② 返回键圆形修复**（四个模拟器 index.html，`.back-btn::after` / `::before`）：

```css
.back-btn::after {                       /* 原：inset: 0（随容器拉伸 → 椭圆） */
  position: absolute;
  left: 50%;
  top: 50%;
  height: 100%;                          /* 以高度为基准 */
  aspect-ratio: 1;                       /* 强制正方形 → border-radius 999px 恒为正圆 */
  transform: translate(-50%, -50%);
  ...
}
.back-btn::before {                      /* 箭头图标同步改为高度基准 */
  height: 31%;                           /* 原：width: 31% */
  aspect-ratio: 1;
}
```

任意窗口比例下：圆以按钮高度为直径，箭头相对圆的比例恒定；16:9 视口下与原设计完全一致（视觉零变化）。

## 十七、移动端横屏观看策略：竖屏旋转提示 + dvh 视口适配（v2.1，2026-08-23）

### 17.1 需求（部署前最后问题）

项目部署后，手机打开网页时是"自动根据界面调整"还是"设置成横屏观看"？

### 17.2 决策：引导横屏观看 + 横屏内自动等比缩放

**结论：采用"横屏观看"策略**，理由：

1. 全部 35 个页面的 UI 设计、热点坐标（百分比定位）、时间轴、模拟器 HUD 均以 **16:9 横屏**为基准；舞台 `#app-stage` 恒定 16:9 等比缩放。
2. 手机竖屏时舞台宽受限于屏宽（如 6.1 英寸手机竖屏约 390px 宽 → 舞台仅 390×219px），界面元素缩至不可用，上下大片空白——"竖屏自动调整"没有可行方案（重排 35 页的响应式改造成本与回归风险极高）。
3. 横屏后舞台按屏幕短边自适应（`min(100vw, calc(100vh * 16/9))`），所有内容**等比缩放、热点对齐关系完全不变**——即"横屏 + 自动缩放"两者兼得。

实现方式为**竖屏旋转提示遮罩**（行业标准做法）：手机竖屏时显示全屏提示"请将手机横屏观看"（带旋转手机图标动画），用户转横后遮罩自动消失，页面自动适配。不采用 `screen.orientation.lock()`：该 API 仅在安卓全屏/安装态生效，iOS Safari 完全不支持。

### 17.3 实现细节

**① 旋转提示遮罩**（`src/App.vue`，纯 CSS 媒体查询驱动，无 JS 状态）：

```css
.rotate-prompt {
  position: fixed;
  inset: 0;
  z-index: 9999;          /* 高于一切：舞台(z1)、Teleport 模拟驾驶层(z2)、品牌 Logo(z50) */
  display: none;          /* 默认隐藏 */
  background: var(--color-bg);
  ...
}
@media (orientation: portrait) and (pointer: coarse) {
  .rotate-prompt { display: flex; }   /* 仅「竖屏 + 触屏」显示 */
}
```

- `pointer: coarse` 条件保证**桌面窄窗口（鼠标指针）不会误弹提示**——桌面窄窗口用户可自行拉宽；
- 手机图标为纯 CSS 绘制（9:16 圆角矩形 + Home 条），`rotateHint` 动画 2.6s 循环演示竖→横旋转；`prefers-reduced-motion` 下停用动画；
- 文案：标题「请将手机横屏观看」+ 副文案「本作品为 16:9 横屏交互设计 / 旋转手机后自动适配屏幕」；
- 尺寸用 `vmin`/`clamp` 弹性适配不同手机屏幕。

**② 移动端视口修正**：

| 文件 | 修改 | 目的 |
|---|---|---|
| `index.html` | viewport meta 增加 `viewport-fit=cover`、`maximum-scale=1.0, user-scalable=no`；`lang="en"` → `zh-CN` | 刘海屏全屏渲染；禁双击缩放（与四个模拟器一致，防止缩放破坏热点对齐）；语言标识修正 |
| `src/App.vue` | `#app-root`/`#app-stage` 增加 `100dvh` 回退声明 | 手机浏览器地址栏收展会改变可视高度，`100vh` 会导致底部被裁/露黑，`100dvh` 动态跟随 |
| `src/style.css` | `#app-stage` 的 `!important` 尺寸规则同步加 `100dvh` 回退 | 同上（该规则带 !important，须成对更新） |

dvh 采用「先 vh 后 dvh」双声明模式：老浏览器忽略不认识的 dvh 行回退到 vh，新浏览器用 dvh；桌面端两者等值，视觉零变化。

### 23.3 慢因定位（按可能性排序）

本地实测各项都快，"打开慢"的感受来自以下场景：

1. **Vite dev server 冷启动后的首次访问**：每次重启 dev server（或改依赖）后第一次打开页面，Vite 需做依赖预构建 + 按需编译，等待数秒属 dev 模式固有开销，之后同页访问 <120ms。这最符合"有时打开慢"的描述。
2. **Windows Defender 实时防护**：项目位于 `WeChatFiles` 目录，杀毒软件对大文件（视频/模型）首次读取有扫描开销，重启电脑后首次访问更明显。
3. **视频出画前的黑屏感知**：视频虽 39ms 就绪，但浏览器解码 + 自动播放降级检查期间页面无任何视觉反馈，主观感觉"空白等待"。
4. **部署到服务器后的真实瓶颈（最重要）**：静态资源总计 2.48GB（课程视频最大单文件 103MB、3D 模型 78MB），全部按需加载不拖累首屏，但——
   - 首屏必须下载 4.3MB 视频：10Mbps 带宽约 3.5s、20Mbps 约 1.8s 才能出画；
   - 各页面大图（5–52MB 组图）与课程视频在访问到时才加载，带宽小则逐页等待；
   - 无 Service Worker/强缓存策略，用户清缓存后全部重来。

### 23.4 部署优化建议（按收益排序，均为服务器配置/资源层，不改代码结构）

1. **服务器开启 gzip/brotli 压缩 + 强缓存头**：JS/CSS 可再减 60–70%；静态资源设 `Cache-Control: max-age=31536000, immutable`（文件名带 hash），回访秒开。
2. **首屏视频瘦身**：4.3MB/720p 可压到 ~2MB（H.264 CRF 提升）或转 720p WebM（约再减 30%），首画出画时间减半。
3. **大组图压缩**：单张 5–52MB 的 PNG 组图转 WebP（无损约省 30%，有质损容忍可省 60%+），整站流量显著下降。
4. **课程视频按需不变已是最佳实践**（懒加载 + 点击才播）；如需更快可转 H.265/H.264 统一码率（当前部分视频码率偏高）。
5. **可选**：首页视频加首帧海报图（poster）消除黑屏感知。

### 23.5 结论

代码架构无性能缺陷（懒加载/分包/入口全部健康）；本地"慢"主要为 dev 冷启动与杀毒扫描的固有开销；**部署后的加载速度由服务器带宽与资源压缩决定**，按 23.4 优化后 10Mbps 带宽即可流畅体验。

## 二十四、后端 LLM 供应商 DeepSeek → Qwen 切换（v2.9，2026-08-26）

> 本章起联调基线切换为 V2 目录：前端 `整个挑战杯的内容V2\挑战杯前端`、后端 `整个挑战杯的内容V2\挑战杯`（2026-08-28 起后端基线由"挑战杯后端第二版"切换为"挑战杯"）。

### 24.1 需求

联调前先修改后端：将回答生成管线调用 DeepSeek 的模型改为调用 Qwen（阿里云百炼 DashScope）。

### 24.2 架构现状与切换方案

第二版后端 LLM 调用链：`configs/providers.yaml`（供应商配置）→ `core/runtime_settings.py`（读 `providers.llm.default`，该读取本身是供应商无关的）→ `src/services/model_factory.py`（创建客户端，原仅支持 deepseek/mock）→ `src/services/deepseek_client.py`（**通用 OpenAI 兼容 HTTP 客户端**：base_url + chat_path + Bearer key + response_format json_object）。

由于客户端实现本就是标准 OpenAI 兼容协议，而 DashScope 提供 OpenAI 兼容端点（compatible-mode），切换只需三处改动（deepseek 配置块完整保留，改一行 default 即可切回）：

### 24.3 修改内容（3 个文件 + 2 个测试）

**① `configs/providers.yaml`**
- `providers.llm.default`: `deepseek` → `qwen`
- 新增 `providers.llm.qwen` 供应商块：`model_id: qwen-plus`（可用 QWEN_MODEL 环境变量换成 qwen-max/qwen-flash）、`api_key_env: DASHSCOPE_API_KEY`（与 embedding 区 qwen 块共用同一把百炼密钥）、`base_url: https://dashscope.aliyuncs.com/compatible-mode/v1`（OpenAI 兼容端点，注意与 embedding 的 native 端点不同）、`chat_path: /chat/completions`、`temperature: 0.2`
- deepseek 块原样保留（回滚开关：default 改回 deepseek 即可）

**② `src/services/deepseek_client.py`**
- `DeepSeekClientConfig` 新增 `provider_name` 字段（默认 "deepseek"，向后兼容）；`from_settings()` 参数化 `prefix`（默认 `providers.llm.deepseek`）——同一客户端类可按任意供应商块构造
- `ModelResult.provider` 由硬编码 `"deepseek"` 改为 `self.config.provider_name`（评估/记忆记录中的供应商标识随配置准确输出）
- 说明：`_log_model_error()` 的 stderr 诊断日志仍打印字面 "deepseek"（该处替换被跳过，不影响功能，仅日志标签）

**③ `src/services/model_factory.py`**
- 供应商白名单扩展：`provider not in ("deepseek", "qwen")` 才报错
- temperature 读取路径、配置前缀、env 兜底填充全部改为 `f"providers.llm.{provider}"` 动态拼接（`_resolve_deepseek_env` 更名 `_resolve_provider_env` 并增加 provider 参数）

**④⑤ 测试同步**（`test_model_client.py` 字段集合断言加入 `provider_name`；`test_encoding_and_config.py` 官方供应商断言改为 qwen 默认 + 新增 qwen 明文密钥路径检查）
