## 一、逐页口播稿（每页 30–40 秒）

### P1 封面（约 30 秒）

各位评委老师好。我们的项目是"翼览无余"——一个面向航空科普场景的证据驱动智能导师。
它的核心承诺是三句话：回答有证据、可追溯、经自检。也就是说，系统给出的每一条事实，
都能指到知识库里的出处；每一轮回答，都经过了检索证据、证据门判定、自检复核的完整链路。
今天我从问题定义、系统架构、两个核心创新、实测数据、合规边界和演进路线六个部分向大家汇报。

### P2 问题定义（约 40 秒）

我们的用户是航空科普场景下的学习者，其中不少是未成年人。这个场景对问答系统提出了
一般聊天机器人不需要面对的要求：第一，**不能编造**——参数类问题没有权威证据时，
系统必须明确说"资料不足"，而不是给一个听起来合理的数字；第二，**必须可解释**——
每个结论要能追到来源，家长和老师才能放心；第三，**过程要可审计**——证据链、自检报告、
改写记录都要留痕。这也是我们为什么没有选择端到端语音大模型：它的音频生成流是一个黑盒，
无法在流内插入"检索证据、证据门、自检、审计"这些确定性环节。这个选型论证记录在
我们的一号架构决策文档里。

### P3 总体架构（约 40 秒）

系统采用 LangGraph 状态机编排文本主链：输入理解、记忆上下文、RAG 证据检索、证据门、
回答生成、自检、反馈改写，最后是语音交互。AppPipeline 是文本和语音的唯一公共边界。
记忆系统当前运行在本地 SQLite 后端；我们完成了 Java 权威侧 M0 到 M5 的全部开发与契约测试，
包括加密、遗忘和图投影，它通过四个阶段的灰度状态机切换，目前还没有切流——这个我们如实说明。
语音链路采用级联选型：本地 faster-whisper 做语音识别，中间走完整文本问答流水线，
再用 edge-tts 合成语音。语音只是入口和出口，事实链始终留在可审计的文本流水线内。

### P4 证据门与状态机（约 40 秒）

检索层有四个当前启用的通道：关键词、稠密向量、父子块和表格；场景、视觉、图谱三个通道
目前是协议预留、数据未入库，没有启用。多路结果经过 RRF 融合、七特征重排，最后进入
四态证据门：confident、weak、conflict、unclear。门控是"默认拒绝"的语义——只有已审核来源
能作核心证据；证据不充分时，系统宁可澄清追问，也不输出确定回答。每一轮回答的状态流
从输入接收到最终就绪，全部记录在运行追踪里，可以导出审计。

### P5 核心创新一：fail-closed 证据门控闭环（约 40 秒）

第一个创新是"fail-closed 的证据门控闭环"。一句话概括：**没有合格证据，就拒绝给确定答案**。
证据门不是"尽量放行"的过滤器，而是"默认拒绝"的安全闸。我们用 100 道题做了独立复核：
请一个独立的语言模型裁判，逐题判断"被放行的回答是否被证据支撑、被拦下的回答是否本来能答对"。
结果是：误拦率 0%，漏拦率 0%——也就是说，门放行的 71 个回答没有一个是错的，
门拦下的 29 个弱证据案例没有一个是能正确作答却被冤枉的。这正是我们想证明的：保守，
而且保守得有理有据。

### P6 核心创新二：Claim 级自纠错（约 40 秒）

第二个创新是"Claim 级自纠错"。我们不信任整段生成的结果，而是把答案拆成一条条事实主张，
逐条对齐证据：对齐不了的，触发改写或者补检索；用户说"你讲得太专业了"，系统在证据锁定下
做表达层面的改写，来源绑定保持不变；用户质疑某个事实，系统不能直接改口，必须先补检索验证。
这里要说明我们的口径：当前语义对齐用的是确定性的证据校验器，基于词项重叠和否定检测；
基于自然语言推理的语义判定是我们规划中的能力，目前没有启用。这也是我们对"不超标宣称"
原则的坚持——说到什么，就一定做到了什么。

### P7 实测数据（约 40 秒）

实测数据分三块。第一，工程基线：全量自动化测试 1500 个用例，0 失败。
第二，检索指标，90 题评测口径：融合召回率 0.9889，90 题命中 89 题；Recall@3 是 0.70，
MRR 是 0.6173，三项都达到甚至超过我们设定的目标线；我们还做了通道消融和复核运行，
数字完全可复现。第三，可信度指标：faithfulness 平均 4.94 分，满分 5 分，刚才说的
误拦率漏拦率都是 0%。语音部分，我们准备了 20 句真实麦克风实测计划，包含首响延迟、
字错误率和打断成功率，目前数据待回填——在实测完成前，我们不宣称任何语音延迟的量化成绩。

### P8 合规与隐私（约 30 秒）

合规上我们做了三件事。第一，许可边界：TTS 组件 edge-tts 实证是 LGPL-3.0 许可，
我们采用标准依赖声明、不修改不分发其源码，不触发传染。第二，出境边界：送往外部的文本
只有答案的口语投影三个字段，不含用户原始转写和语音；原始音频本地处理、默认不落盘，
而且这个开关在配置加载阶段就被代码硬性拒绝，改配置也绕不过去。第三，未成年人保护：
记忆默认不授权长期存储、默认 30 天过期、隐私惩罚权重最高。诚实边界我们也写明了：
系统目前没有实名和年龄门禁，正式商用前需要按法规补充监护人同意流程。

### P9 演进路线（约 30 秒）

短期三步：完成 20 句真实语音实测回填；按预检清单完成现场预检和三次模拟答辩彩排；
推进 Java 记忆服务灰度切流。中期：数字人 3D 端 SDK 对接——这里口径是协议已定义、
对接是下一阶段的工作，我们不在今天宣称这个能力；以及多模态通道按需启用、NLI 语义判定评估。
长期：生产部署与真实模型评测。我们的原则始终是：能力边界如实标注，实测数据先测后说。
谢谢各位老师，欢迎提问。

## 二、7 类灵魂拷问成文应答

> 与 `docs/答辩/现场预检清单.md` 附录共用；每问给出"结论 + 依据 + 边界"三段式，引用任务产物。

### Q1 密钥与安全：代码里有没有硬编码密钥？现场没网怎么办？

- **结论**：仓库无任何密钥。密钥一律通过环境变量注入（`DEEPSEEK_API_KEY` 等，
  `configs/providers.yaml` 只声明 `api_key_env` 引用）；提交前 `scripts/check_secrets.py`
  门禁扫描，T02 已清除历史明文残留。
- **依据**：T02（配置与密钥清理）、`scripts/check_secrets.py`、`docs/项目总控/密钥扫描使用说明.md`。
- **边界**：无密钥环境自动 fail-closed 降级 mock LLM，回答不因缺密钥而"瞎编"；
  离线兜底演示用 `scripts/demo_offline.py`（T14），一条命令跑通检索→证据门→自检→产出，
  强制全 mock、不读任何密钥环境变量，可断网运行。

### Q2 延迟：首响延迟多少？实时性够吗？

- **结论**：真实首响延迟**待回填，来源 T13**——20 句真实麦克风实测的均值与 p95，
  达标线 ≤5 秒；二次对话（指代追问轮）≤3 秒。在实测回填前，我们不宣称任何量化成绩。
- **依据**：`docs/评测与验收/语音实测报告.md`（T13 模板，实测数据列全部待回填）。
- **边界**：架构层面采用"级联延迟预算"叙事（ADR-025）：本地 ASR 无网络往返 + 文本流水线
  单轮检索生成 + 流式 TTS 分块播放，语音输出受 20 秒/180 字符硬约束；若实测未达标，
  语音链路表述为"安全级全量自检模式"——宁肯首响延迟超预算，也不跳过证据门与自检（T13 模板 §4.2）。

### Q3 数字人：有数字人形象吗？多模态交互呢？

- **结论**：数字人**协议已定义，3D 端 SDK 对接为下一阶段**（T26 口径）；本次答辩不展示数字人。
- **依据**：T26 口径记录、`docs/评测与验收/release_acceptance.md` 已知缺口表（数字人行）。
- **边界**：多模态通道（visual/scene/graph）为协议预留、`enabled:false`、数据未入库（T18/T26）；
  我们只宣称已实现的级联语音链路（faster-whisper 本地 ASR + edge-tts TTS + 打断）。

### Q4 知识审核：知识库内容可靠吗？AI 会不会学到错误知识？

- **结论**：知识库 404 条来源全部为 `reviewed` 审核状态；已按机型分层抽样 84 条
  （20.79%，≥20% 达标）做人工抽检，机械检查 84/84 通过（元数据/引用/清单一致性），
  结论留痕表待人工填写审核人三要素（T19）。
- **依据**：T19 知识库抽检报告（`docs/评测与验收/知识库抽检报告.md`）。
- **边界**：证据门只允许 reviewed 来源作核心证据（`allowed_core_review_status: [reviewed]`）；
  运行库与治理清单存在"candidate/reviewed 未回写"的治理口径问题，已列入待确认并给出回写脚本
  （`scripts/annotate_review.py`）；AI 不能把用户说法、记忆内容当作航空事实（记忆只影响表达，
  事实只来自 evidence_package，spec 全局原则）。

### Q5 评测口径：这些数字是真实评测还是自己编的？

- **结论**：全部为真实运行实测，口径透明可复现。检索指标为 90 题评测集
  （排除 10 道无黄金答案的弱证据题，口径变更原因已写入报告 §10.1）；
  T22 做了分母并列与通道消融，复核组与基线完全一致（0.9889/0.7000/0.6173 可复现）。
- **依据**：T17/T22（`docs/评测与验收/评测报告/rag_100q_bench_report.md`）、T23 faithfulness 补测。
- **边界**：评测为本地离线 bench（`scripts/_rag_bench.py` 只读知识库、产物在 tmp/ 不入库），
  不代表生产环境线上评测；faithfulness 用 LLM-as-judge 逐题复核（每题 1 次调用，temperature 0.2），
  100/100 题返回有效 JSON、0 解析错误。语音实测数字未回填前不展示（T13）。

### Q6 测试失败：1500 个测试全过？之前失败过怎么办？

- **结论**：当前 `pytest tests/ -q` 为 **1500 collected / 0 failed**（T05）。
  此前 T04 基线有 31 个失败，全部按六类归因（断言过期/环境依赖/CLI 契约/集成超时/
  脚本门禁/输出泄漏），逐类修复清零，未删除测试、未削弱断言、未新增 skip/xfail。
- **依据**：T04/T05 记录（`docs/项目总控/STATUS.md`）。
- **边界**：修复中发现的预存在问题（如 T29 全局锁掩盖的检索层共享 sqlite 连接非线程安全）
  以最小复现 + 真实并发断言修复（per-session 锁 + 检索存储串行锁，LLM 阶段跨会话并行）；
  harness 禁止"借机修复"清单外文件，发现即记录待确认，不带着失败推进。

### Q7 创新点：和普通 RAG 问答系统比，你们的独特之处是什么？

- **结论**：三点。① **fail-closed 证据门控闭环**——证据门默认拒绝，无证据不输出确定答案，
  且经 T23 独立复核误拦率/漏拦率双 0%；② **Claim 级自纠错**——逐条主张对齐证据、
  未对齐触发改写/补检索，反馈改写锁定证据、事实挑战必须补检索（P5/P6）；
  ③ **可信优先的级联语音**——拒绝端到端黑盒模型，语音两端文本化、中间全链路可审计（ADR-025）。
- **依据**：P4/P5/P6 规格、T23、ADR-025。
- **边界**：我们刻意不宣称多模态、数字人、NLI 语义判定等未落地能力（T26 口径）；
  创新点在于"工程化的可信闭环 + 可量化的门控验证"，而非单一算法突破。
