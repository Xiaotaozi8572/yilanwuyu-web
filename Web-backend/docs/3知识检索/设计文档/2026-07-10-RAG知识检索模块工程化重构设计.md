## 2. 设计目标

本设计用于解决当前知识检索模块与《翼览无余智能体模块设计文档V2_增加语音交互.docx》第 7 章之间的落地差异。重构不是把现有 Mock 组件更换名称，而是让系统具备真实可运行的知识入库、索引构建、混合召回、融合重排、证据门控、定向补检索和审计闭环。

重构完成后必须满足以下核心判断：

1. 默认应用启动后能够从持久化知识仓储装载已审核航空资料，而不是依赖测试代码手工注入片段。
2. 关键词、稠密向量、场景对象、父子节点、视觉页面和轻量图谱均通过统一检索通道接口参与规划与召回。
3. 检索融合采用可解释的 RRF，重排序显式考虑相关性、场景匹配、来源权威、版本时效、模态互证和 claim 支持能力。
4. `EvidenceGate` 能区分 `confident`、`weak`、`conflict`、`unclear`，不能因为命中一条 reviewed 片段就默认认为复杂问题证据充分。
5. `evidence_package` 包含完整来源、定位、支持类型、缺失证据、冲突证据、生成边界和审计轨迹。
6. `RETRIEVE_MORE` 必须基于缺失原因生成新的 verification query、调整通道或预算，不能重复相同检索计划。
7. 记忆只提供检索意图辅助和教学适配信号，不能成为 `EvidenceItem`，表达偏好不能直接污染事实查询。
8. 所有 top-k、阈值、权重、Provider、数据库路径和通道开关均由 `configs/rag.yaml` 驱动。

### 4.2 当前主要问题

| 问题 | 当前表现 | 影响 |
| --- | --- | --- |
| 知识仓储为空 | `data/raw_sources` 没有正式资料，默认 `AppPipeline` 不装载知识 | 默认应用只能返回资料不足 |
| 入库不持久化 | `scripts/ingest_sources.py` 只创建内存对象并打印数量 | 进程退出后来源和索引丢失 |
| 切片非语义化 | 固定 400 字符、80 字符重叠，`parent_id` 未赋值 | 定义、条件和上下文可能被切散 |
| 关键词非 BM25 | 中文逐字与少量硬编码短语重合 | 长文档和常见词排序质量不足 |
| 向量为 Mock | 8 维字符哈希，不能表达真实语义 | 口语和同义表达召回不可靠 |
| 融合非 RRF | 多个 query variant 的分数直接累加 | 通道分数不可比，重复查询会放大得分 |
| 计划不自适应 | 所有问题固定调用三条文本通道 | 参数题、部件题、原理题、综述题无法差异化处理 |
| 通道字段未执行 | `RetrievalPlan.channels` 未被控制器读取 | 计划只是声明，不是真正路由 |
| 视觉和图谱未接线 | 类存在但 `RetrievalController` 不调用 | 不能形成 Word 文档要求的多模态和图谱证据 |
| Gate 状态不完整 | 实际只有 confident/weak | 无法表达冲突、对象不清和覆盖不足 |
| 证据包字段不完整 | `claim_support_map` 为空，缺来源定位和真实权威等级 | 自检与答辩展示无法完整追溯 |
| 补检索无增量 | `RETRIEVE_MORE` 重复相同计划 | 循环消耗预算但不增加证据 |
| 配置未生效 | `rag.yaml` 未被控制器加载 | top-k、阈值、Provider 等仍由代码默认值决定 |

## 5. 重构原则

### 5.1 事实来源单一

事实性 claim 只能由 `EvidencePackage.evidence_items` 中 `usable_as_core_evidence=true` 的证据支持。以下内容不得转换为航空事实：

- 用户历史说法；
- 用户反馈；
- 学习者偏好；
- Prompt 正文；
- 模型自由生成内容；
- 未审核视觉识别标签；
- draft、candidate 或 deprecated 来源；
- 缺失 source_id 或原始定位的网页摘录。

### 5.2 接口先行、实现可替换

业务层只依赖 `KnowledgeRepository`、`RetrievalChannel`、`EmbeddingProvider`、`VectorStore`、`DocumentParser` 等协议，不直接依赖 Qdrant、Milvus、Neo4j、RAGFlow 或某个模型 SDK。

默认离线实现使用：

- SQLite 持久化来源、片段、父节点、场景对象、视觉资产和图谱边；
- SQLite FTS5 提供 BM25；
- SQLite 向量表保存 embedding，并在中小规模知识库中执行余弦检索；
- 现有 `EmbeddingProvider` 注入 embedding，offline profile 允许 Mock，production profile 禁止 Mock；
- SQLite 图表提供一到两跳轻量图谱检索。

该选择不引入大型服务依赖，符合当前 harness；后续可在保持接口不变的前提下替换为 Qdrant、Milvus 或 Neo4j。

### 5.3 配置必须真实生效

`configs/rag.yaml` 是 RAG 运行时唯一配置入口。生产代码不得在构造器中散落 top-k、阈值、权重和通道默认值。配置缺失或非法时必须抛出结构化 `ConfigError`。

### 5.4 检索计划与执行分离

`RetrievalPlanner` 只负责理解问题、分级、生成查询和选择通道；`RetrievalExecutor` 只执行计划。通道失败时返回结构化结果，不能在控制器中静默切换算法。

### 5.5 检索 Gate 与自检分工

- `EvidenceGate` 判断证据包是否足以进入生成。
- `SelfCheck` 判断生成后的答案是否正确使用证据。
- `EvidenceGate` 不检查最终答案表达。
- `SelfCheck` 不直接重建索引或写入知识库。

### 5.6 分阶段交付

升级顺序固定为：

```text
配置与持久化
→ 文本入库与父子节点
→ BM25 + 稠密向量
→ 自适应规划 + RRF + 重排
→ 完整 EvidenceGate 和证据包
→ 场景对象与图谱
→ PDF/视觉页面
→ 定向补检索与全链路验收
```

不得在文本主链路不稳定时提前引入多模态或外部向量服务。

## 9. 持久化设计

默认使用 `data/processed/knowledge.sqlite3`，与记忆数据库分离，禁止知识事实和用户记忆共表。


要求：

## 10. 入库流程

### 10.1 标准流程

```text
原始资料登记
→ 计算 content_hash
→ 来源审核状态检查
→ 文档解析
→ 语义父节点构造
→ 子片段切分
→ 元数据抽取与校验
→ 写入 repository
→ BM25 索引
→ embedding 构建
→ 场景/视觉/图谱关联
→ 生成 index version
→ 运行入库质量检查
```

### 10.2 语义切片

切片优先级：

1. 标题与章节边界；
2. 自然段；
3. 列表、表格和图注边界；
4. 句子边界；
5. 只有单个语义块超长时才使用字符窗口。

默认目标长度为 300-600 中文字符，重叠 60-100 字。重叠只能在同一父节点内发生，不能跨章节拼接。

### 10.3 PDF 与图文资料

第一阶段实现 PDF 文本、页码、页面顺序和基础 layout trace；扫描 PDF、OCR、页面图像 embedding 和复杂表格解析必须通过依赖审批后启用真实 Provider。

任何无法形成 layout trace 的视觉描述必须标记：

```text
usable_as_core_evidence = false
incomplete_reasons += ["missing_layout_trace"]
```

## 11. 索引设计

### 11.1 BM25 关键词索引

使用 SQLite FTS5 `bm25()`，航空术语、型号、部件别名通过可配置词典在入库和查询时标准化。FTS5 不可用时启动检查直接失败，不能静默伪装成 BM25。

### 11.2 稠密向量索引

所有 embedding 由 `EmbeddingProvider` 生成，并记录：

- provider；
- model；
- dimension；
- is_mock；
- created_at；
- content_hash。

offline profile 可以使用 Mock 运行测试，但 evidence audit 必须标记 `embedding_is_mock=true`。production profile 检测到 Mock 时禁止生成 confident 语义-only 证据。

### 11.3 父子索引

子片段用于精确召回；当同一父节点命中达到阈值或问题复杂度为 L3-L5 时，加入父节点摘要和相邻片段。父节点不能替代原始子片段来源，EvidenceItem 必须同时保存 parent_id 和 supporting_chunk_ids。

### 11.4 Scene 索引

SceneObject 不是单纯后置 component 过滤器。检索时应先通过 scene_object_id 取得 linked_chunk_ids、linked_visual_asset_ids 和 linked_concepts，作为独立场景通道候选。

### 11.5 视觉页面索引

视觉页面通道检索 caption、OCR、visual labels 和页面 embedding。视觉命中必须与文本、表格或图谱证据配对后才能成为核心事实。

### 11.6 图谱索引

图谱通道支持一到两跳，并按 relation_type 白名单扩展。检索返回图路径后必须回查 edge.source_id 和关联文本，不允许图谱路径脱离来源直接进入答案。

## 12. 查询理解与自适应检索计划

### 12.1 问题复杂度

| 等级 | 问题类型 | 默认通道 |
| --- | --- | --- |
| L1 | 简单事实、术语定义 | BM25 + dense + metadata |
| L2 | 场景指代、部件定位 | scene + BM25 + dense |
| L3 | 原理解释 | dense + parent + visual + BM25 |
| L4 | 对比、误解纠正 | BM25 + dense + graph + parent |
| L5 | 跨资料综合、全局问题 | multi-query + parent + graph + visual + BM25 + dense |

### 12.2 查询变体

每轮最多生成以下四类查询：

1. `exact_query`：标准术语、型号和参数表达。
2. `user_query`：保留用户原始口语表达。
3. `scene_query`：使用 scene_object_id、aircraft、component、linked concepts。
4. `principle_query`：只扩展已识别意图，不创造未经证实的型号或参数。

记忆中的 misconception 可以补充纠正主题；`educational_wording`、类比偏好和回答长度偏好不得加入事实查询，只能进入 pedagogical fit。

### 12.3 RetrievalPlan

```text
plan_id
query_text
query_variants
complexity_level
channels
filters
channel_top_k
fusion_top_k
rerank_top_k
scene_object_id
required_evidence_types
retrieval_budget
verification_reason
loop_count
```

`channels` 必须由执行器逐项读取。配置关闭的通道不得被调用，计划未列出的通道不得被隐式执行。

## 13. 召回、融合和重排序

### 13.1 召回结果统一结构

```text
RetrievalHit:
  item_id
  channel
  rank
  raw_score
  normalized_score
  query_variant
  source_id
  metadata
  is_mock
```

### 13.2 RRF

融合使用：

```text
rrf_score(d) = Σ 1 / (k + rank_channel(d))
```

默认 `k=60`，通过配置调整。缺席通道不贡献分数，不能把不同通道的 raw score 直接相加。

### 13.3 重排序特征

最终重排分数使用配置化权重：

```text
query_relevance
scene_match
source_authority
modality_support
claim_support
freshness_version
pedagogical_fit
```

其中 pedagogical fit 只决定同等事实证据的呈现优先级，不能使低权威或不相关证据超过核心事实门槛。

### 13.4 父子上下文合并

若同一父节点有多个高排名子片段，则生成一个 ContextGroup：

```text
parent_id
supporting_chunk_ids
parent_summary
ordered_context
coverage_tags
```

合并不能删除原始 evidence_id，避免来源链断裂。

## 14. EvidenceGate 设计

### 14.1 confident

同时满足：

- 至少一条 reviewed 核心证据；
- required evidence types 达到配置要求；
- 无未处理的高风险冲突；
- 场景对象明确或问题不依赖场景；
- 参数问题存在带来源、单位和版本的参数证据；
- Mock-only 语义命中不能单独构成 confident。

### 14.2 weak

证据与问题相关，但缺少关键结论、限定条件、参数、互证或覆盖范围。必须填充具体 `missing_evidence`。

### 14.3 conflict

两个 reviewed 来源对同一 claim 给出不兼容结论，且无法通过版本、适用机型或权威等级消解。输出 contradiction evidence，并路由到 HUMAN_REVIEW 或保守说明。

### 14.4 unclear

目标飞机、部件、场景对象或用户意图不明确。必须提供 clarification reason 和候选对象，不进入确定性事实生成。

## 15. 定向补检索设计

`RETRIEVE_MORE` 必须携带 `RetrievalFeedback`：

```text
reason
unsupported_claims
missing_evidence
previous_plan_id
previous_evidence_ids
recommended_channels
budget_delta
verification_queries
```

补检索规则：

- 缺参数：优先 BM25、table 和高权威来源。
- 缺场景绑定：优先 scene registry，无法唯一绑定则 ASK_CLARIFICATION。
- 缺原理上下文：扩大 parent 和 graph 通道。
- 视觉无文本互证：补检索 linked text/table/graph。
- 事实挑战：生成只围绕被挑战 claim 的 verification queries。
- 第二次计划必须与第一次在 query、channel、filter 或 budget 至少一项不同。
- 达到循环上限后输出保守结果，不继续重复检索。

- embedding provider/model/is_mock；

## 18. 错误处理与降级

| 异常 | 行为 |
| --- | --- |
| 配置缺失或非法 | 返回 `rag_config_error`，阻止启动 |
| SQLite 不可写 | 返回 `knowledge_repository_unavailable`，不创建空知识库冒充成功 |
| FTS5 不可用 | 返回 `keyword_index_unavailable`，不把字符重合描述为 BM25 |
| embedding provider 不可用 | offline 可显式启用 fallback；production 返回结构化错误或只用非语义通道并降级 Gate |
| scene_object_id 不存在 | `unclear` + clarification reason |
| 来源未审核 | 候选可记录但不得进入核心证据 |
| 图谱边缺来源 | 排除并记录 `graph_edge_without_source` |
| 视觉缺 layout trace/text cross-check | 辅助线索或 incomplete，不作为核心事实 |
| 多来源冲突 | `conflict`，不静默选择单一来源 |
| 补检索无新增信息 | 停止循环并输出保守说明 |

## 19. 安全与权限边界

- 只有入库服务可以写 `knowledge.sqlite3`。
- `RetrievalController` 只读知识库。
- 反馈模块、记忆模块和 Prompt 模块不能直接调用 repository 写事实。
- 用户上传资料默认是 candidate，必须审核后才能成为核心来源。
- 真实外部 Provider 的密钥只从环境变量读取，不写配置文件或 trace。
- 原始资料路径和页面截图不得包含超出项目范围的私密文件。
- trace 只记录证据摘要和 ID，不复制整份受版权保护文档。

## 20. 迁移策略

### 20.1 保留

- `SourceRecord`、`TextChunk`、`SceneObject`、`RetrievalPlan`、`EvidenceGateResult` 的概念边界。
- `EmbeddingProvider`、`VectorStore` 协议。
- reviewed 来源门控。
- 视觉 text cross-check 规则。
- `EvidencePackage` 顶层契约。
- Agent 状态机和自检模块边界。

### 20.2 替换

- `SourceRegistry` 内存字典替换为 repository-backed registry。
- 固定字符切片替换为语义父子切片。
- `KeywordIndex` 重合计数替换为 FTS5 BM25。
- 自定义分数累加替换为 RRF + rerank。
- 只有 confident/weak 的 Gate 替换为四态 Gate。
- `RETRIEVE_MORE` 重复计划替换为 feedback-driven replan。

### 20.3 删除

- 验收完成后删除 `SimpleVectorIndex` 在 production 路径中的使用。
- 删除不再使用的 `evidence_ranking.py` 旧融合实现。
- 删除只打印数量、不写持久化仓储的旧演示入库路径。
- 删除与新 repository 重复的内存 source/scene 存储生产路径。

## 21. 测试设计

### 21.1 单元测试

- RagConfig 加载、类型校验、权重校验和路径校验。
- Source 生命周期、content hash 去重、deprecate 和版本记录。
- 语义切片不跨章节、父子关系和顺序稳定。
- FTS5 BM25 排序。
- SQLite vector store 持久化与元数据过滤。
- 查询复杂度 L1-L5 与通道路由。
- RRF 的通道分数不可比问题。
- 七类 rerank 特征和权重。
- Gate 四态覆盖。
- scene linked chunk 召回。
- graph edge source 回溯。
- 视觉缺交叉验证时不可成为核心证据。
- 定向补检索必须产生不同计划。

### 21.2 集成测试

- 正式入库脚本写入 SQLite，重启控制器后仍能检索。
- 精确术语走 BM25，口语表达走 dense。
- selected_object_id 走 scene 通道并召回 linked chunks。
- 原理问题召回父节点上下文。
- 对比问题使用 graph + text 证据。
- weak 补检索后升级 confident，或保持 weak 并说明具体缺失。
- conflict 路由 HUMAN_REVIEW。
- 默认 AppPipeline 能从配置路径装载知识仓储。
- memory 只能改变检索意图和教学适配，不能生成 EvidenceItem。

### 21.3 E2E 与评测

- C919 机翼升力。
- C919 发动机涵道比。
- AG600 船型机身场景问题。
- 升力与推力对比纠错。
- 无审核参数时拒绝输出具体数值。
- 低置信语音不进入正式检索。
- 用户事实挑战触发定向 verification query。

## 22. 验收标准

重构完成必须同时满足：

1. `configs/rag.yaml` 的关键配置均有运行时读取测试。
2. 默认 AppPipeline 能装载持久化 reviewed 示例知识，不依赖测试手工 `add_chunks()`。
3. 重启进程后来源、父节点、片段、embedding、scene 和 graph 数据仍存在。
4. 精确术语、口语表达、场景对象、原理问题和对比问题分别命中预期通道。
5. 融合实现是 RRF，不再把 raw score 直接相加。
6. Gate 四态均有测试，复杂问题不会因一条证据自动 confident。
7. `EvidenceItem` 包含真实 authority、modality 和 original location。
8. `claim_support_map`、missing evidence、contradiction evidence 和 generation boundary 均有内容测试。
9. RETRIEVE_MORE 的新计划与旧计划存在结构化差异，并受循环上限控制。
10. 视觉无 text cross-check、图谱边无 source_id、用户反馈来源均不能成为核心事实。
11. RAG 专项测试、相关集成测试、全量 pytest、compileall、smoke eval 和 trace export 全部通过。
12. `docs/项目总控/STATUS.md` 记录修改文件、测试命令、测试结果、harness 检查和剩余限制。

## 23. 分阶段交付建议

| 阶段 | 交付内容 | 可独立验收结果 |
| --- | --- | --- |
| RAG-1 | typed config + SQLite repository | 配置真实生效、来源与片段可持久化 |
| RAG-2 | 语义父子切片 + BM25 + SQLite vector | 文本知识库重启后可混合召回 |
| RAG-3 | 自适应 Planner + RRF + rerank | 不同问题走不同通道，融合可解释 |
| RAG-4 | 四态 Gate + 完整 evidence package | 缺失、冲突、澄清和生成边界可审计 |
| RAG-5 | Scene + graph | 3D 对象与关系问题进入真实检索通道 |
| RAG-6 | PDF/视觉页面 | 页面、bbox、OCR/caption 和文本互证可追溯 |
| RAG-7 | 定向补检索 + 全链路验收 | RETRIEVE_MORE 能增加信息而非重复循环 |

每个阶段都必须先完成测试和 STATUS 记录，再进入下一阶段。OCR/layout、真实外部 embedding、Qdrant/Milvus/Neo4j 等依赖若未获批准，必须停在对应依赖门，不得静默扩大范围。

## 24. 需要调用的 skill

实施本设计时按以下顺序使用：

1. `using-superpowers`：每个阶段开始前发现适用工作流。
2. `writing-plans`：以本设计为依据维护逐任务实施计划。
3. `subagent-driven-development`：仅在用户明确授权子智能体执行时，按独立任务推进。
4. `systematic-debugging`：遇到测试失败、索引结果异常、Gate 状态错误或检索链路偏差时定位根因。
5. `pdf`：实施真实 PDF 页面解析、渲染或版面验证时使用。
6. `verification-before-completion`：每个 RAG 阶段完成前运行专项与全量验证。

如果需要引入新的大型外部服务或依赖，必须先依据 `harness.md` 停止并请求用户确认。
