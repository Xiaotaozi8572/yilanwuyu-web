# C919 科普问答知识库目录设计

- 文档定位：本轮知识库接入目录设计的唯一交付物，遵循 `docs/知识库构建/CONTEXT.md` 的目录治理语言。
- 交付边界：只产出本设计文档，不创建目录、不迁移资料、不修改入库脚本、不改变 `configs/rag.yaml` 与 `src/knowledge/*` 的运行时契约。
- 适用阶段：第一版仅支撑 C919 的科普问答（science popularization QA），其它型号（J20/Y20/Z20）以对象骨架形式预留，不在本轮填充。
- 对齐代码：目录字段与 `src/knowledge/schemas.py`（`SourceRecord`、`TextChunk`、`ParentDocument`、`VisualPage`、`SceneObject`、`GraphNode`、`GraphEdge`）、`configs/rag.yaml`（7 路检索通道、`gate`、`rerank`）、`scripts/ingest_sources.py`（CLI 参数）一一对应。

## 1. 设计目标与边界

### 1.1 目标
1. 承载 C919 科普问答所需的全部资料治理对象：原始资料、审核清单、入库批次、派生索引说明和评测种子。
2. 让 `01_science` 等成熟分区可独立扫描入库，不要求对象下所有分区同时成熟（`object.yaml` 的 `partition_enable` 开关）。
3. 与项目代码现有 7 条检索通道（keyword/table/dense/parent/scene/visual/graph）一一对应，资料形态与索引消费者对齐，避免出现"有目录无消费者"或"有消费者无资料"的悬空结构。
4. 把审核状态、权威等级、允许用途从文件名里抽离，全部由 `manifest.yaml` 承载，避免目录搬移式审核。

### 1.2 非目标
- 不在本设计里实现入库脚本扫描器，不改 `RetrievalController.from_config`。
- 不在本设计里建库 `data/processed/knowledge.sqlite3` 的内容，只规定资料治理目录。
- 不引入 CONTEXT.md 未定义的新分区名或新对象名。
- 不混入培训/维修/操作类内容作为科普证据源（参考资料一律隔离在 `90_reference_only`）。

## 3. 根级文件规范

### 3.1 `README.md`
内容必须包含：
- 知识库接入目录的定位（科普证据源治理，不是运行产物目录）。
- 目录红线（见第 9 节）。
- 五分区职责一句话定义（来自 CONTEXT.md 的 Language 段）。
- 指向 `SCHEMA.md` 和 `MANIFEST.yaml` 的引用。

### 3.2 `MANIFEST.yaml`（全局资料清单）
对象级聚合视图，不重复最小分区 `manifest.yaml` 的字段，只承担全局对象索引。字段：

```yaml
# data/knowledge_sources/MANIFEST.yaml
schema_version: "1.0"
knowledge_base:
  root: data/knowledge_sources
  default_aircraft: c919
  active_objects:
    - id: c919
      display_name: "中国商飞 C919"
      partition_enable:
        01_science: true
        02_teaching: true
        03_multimodal: true
        04_terms_graph: true
        90_reference_only: false   # V1 不入库参考资料
    - id: j20
      display_name: "歼-20"
      partition_enable: {}          # 骨架对象，所有分区默认关闭
    - id: y20
      display_name: "运-20"
      partition_enable: {}
    - id: z20
      display_name: "直-20"
      partition_enable: {}
  global_review_policy:
    allowed_core_review_status: ["reviewed"]   # 必须与 configs/rag.yaml gate 对齐
    authority_levels:
      official: 1.0
      project_reviewed: 0.8
      standard: 0.6
```

### 3.3 `SCHEMA.md`
最小分区 `manifest.yaml` 的字段词典与示例（见第 7 节），由本设计文档第 7 节内容维护，`SCHEMA.md` 是其镜像，便于人工录入时直接查阅。

### 3.4 `00_inbox/`
- 仅承载刚收集、尚未完成对象归属和 manifest 登记的资料。
- 不作为入库来源，不能被引用为科普证据源。
- `00_inbox/README.md` 必须写明：暂存区资料的归宿是登记到某对象的某分区 `manifest.yaml`，或删除；不允许长期堆放。

## 4. 知识对象层规范

### 4.1 `object.yaml`（对象元数据）
```yaml
# data/knowledge_sources/c919/object.yaml
object_id: c919
display_name: "中国商飞 C919"
aliases:
  - "C919"
  - "国产大飞机"
  - "中国商飞窄体客机"
aircraft_family: "narrow_body"
manufacturer: "COMAC"
partition_enable:
  01_science: true
  02_teaching: true
  03_multimodal: true
  04_terms_graph: true
  90_reference_only: false
partition_owners:
  01_science: "科普证据组"
  02_teaching: "教学设计组"
  03_multimodal: "视觉资产组"
  04_terms_graph: "术语图谱组"
  90_reference_only: "资料转化组"
notes: "V1 仅启用 01-04，90 分区作为资料预留入口。"
```

字段说明：
- `object_id`：机器友好对象 ID，固定为 `c919/j20/y20/z20`。
- `display_name`/`aliases`：对应 `SceneObject.aircraft` 与 `aliases`、`GraphNode.aliases` 的来源。
- `partition_enable`：与 `MANIFEST.yaml.global_review_policy` 共同决定是否参与扫描或入库；分区关闭即等价于"目录存在但不参与本轮入库"。
- `partition_owners`：人工维护责任，不进入代码字段，仅供 `manifest.yaml` 的 `metadata.owner` 校对。

### 4.2 骨架对象（j20/y20/z20）
仅 `object.yaml`，所有 `partition_enable` 为空或全 false。V1 不在骨架对象下创建任何分区目录，避免"空目录即启用"的歧义。

## 5. C919 五分区详细设计

### 5.1 `01_science/`（科普证据源，V1 主填充分区）

对应代码侧：
- 入库主路径 `TextIngestor.ingest_document` → `ParentDocument`/`TextChunk`。
- `TextChunk` 的 `aircraft`、`component`、`concept`、`knowledge_type` 字段必须由 manifest 提供。
- 检索通道：keyword/table/dense/parent 四通道直接消费本分区。

#### 5.1.1 `01_overview/` — 总览
- 内容：型号定位（窄体客机）、设计目标、基本参数（机长/翼展/机高/典型客载/航程/发动机选型）、技术特征概述。
- `knowledge_type`：`overview` / `parameter_fact`（参数类问题必须 `require_parameter_source=true`）。
- `concept` 建议枚举：`model_overview`、`design_goal`、`basic_parameter`、`technology_highlight`。
- 必备资料示例：
  - `c919-overview-2024-reviewed.md`（型号概述，权威等级 official/project_reviewed）
  - `c919-basic-parameters-2024-reviewed.md`（基本参数表，含来源标注）

#### 5.1.2 `02_structure_systems/` — 结构与系统
对应 `SceneObject.component` 与 `TextChunk.component`。建议按系统切分为独立 parent 文档，便于 `parent_index` 与 `scene_object` 绑定。
- 子主题（每个对应一个 `component` 值）：
  - `fuselage` 机体结构
  - `wing` 机翼（含襟翼/副翼/翼尖小翼）
  - `empennage` 尾翼
  - `landing_gear` 起落架
  - `propulsion` 动力系统（CFM LEAP-1C）
  - `avionics` 航电系统
  - `flight_control` 飞控系统（电传操纵）
  - `hydraulic` 液压系统
  - `fuel` 燃油系统
  - `cabin` 客舱系统
- `knowledge_type`：`component_role` / `system_explanation`。
- 必备资料示例：
  - `c919-wing-structure-2024-reviewed.md`
  - `c919-propulsion-leap1c-2024-reviewed.md`
  - `c919-flight-control-architecture-2024-reviewed.md`

#### 5.1.3 `03_principles/` — 原理
对应 `TextChunk.concept` 与 `GraphNode.node_type=concept`。
- 子主题（每个对应一个 `concept` 值）：
  - `aerodynamics` 气动原理（升力/阻力/升阻比/失速）
  - `flight_mechanics` 飞行力学（巡航/爬升/下降/起飞着陆）
  - `engine_principle` 涡扇发动机原理（涵道比/压气机/燃烧室/涡轮）
  - `composite_material` 复合材料原理（应用部位/减重/强度）
  - `fly_by_wire` 电传操纵原理
  - `airworthiness_concept` 适航理念（CCAR-25/审定基线）
- `knowledge_type`：`principle_explanation`。

#### 5.1.4 `04_history_milestones/` — 历史与里程碑
- 子主题：
  - `project_approval` 立项（2008）
  - `development` 研发历程
  - `maiden_flight` 首飞（2017-05-05）
  - `test_flight` 试飞取证（6 架试飞机、上千试飞科目）
  - `certification` 适航取证（2022-09-29 型号合格证）
  - `delivery` 交付与运营（2022-12-09 首架交付东航）
- `knowledge_type`：`milestone_event`。
- 时间敏感字段写入 `metadata.timeline`，供 `freshness_version` rerank 使用。

#### 5.1.5 `05_applications_value/` — 应用与价值
- 子主题：
  - `commercial_value` 商业价值（窄体客机市场、订单规模）
  - `strategic_significance` 战略意义（大飞机自主可控）
  - `supply_chain` 产业链（国产化率、国内外供应商）
  - `technology_spillover` 技术溢出（对支线客机/宽体客机的技术积累）
- `knowledge_type`：`value_analysis`。
- 注意：商业预测类内容必须标注来源与时间窗口，避免进入"无来源的事实证据"。

#### 5.1.6 `06_comparison/` — 对比
对应 `RetrievalPlan.filters.intent_type=comparison`、`required_evidence_types=["comparison"]`。
- 子主题：
  - `vs_b737` 与波音 737 系列（含 MAX）对比
  - `vs_a320` 与空客 A320 系列（含 neo）对比
  - `vs_arj21` 与 ARJ21 支线客机对比（同为 COMAC 产品）
  - `vs_widebody` 与宽体客机的定位区分（避免跨类别误比）
- `knowledge_type`：`comparison`。
- 必备字段：对比维度（机身长度/航程/发动机/客载/技术代际）必须成对出现，便于 `table` 通道消费。

### 5.2 `02_teaching/`（教学组织素材）
对应代码侧：`aviation_quiz_reinforcement`、`experimental_teaching_strategy`、`spoken_answer_style_prompt` 等 prompt 资产的教学侧上下文，不进入科普事实证据链。

- `explanation_plans/`：讲解计划与讲解骨架，按受众（普通公众/中学生/大学生）分层。
- `difficulty_tiers/`：同一主题的入门/进阶/深入三档版本。
- `analogies/`：类比素材库（例：把"涵道比"类比为"齿轮比"）。
- `misconceptions/`：常见误解与纠偏（例：误以为 C919 是"完全自主"而非"自主设计、全球供应链"）。
- `qa_seeds/`：讲解侧问答种子，仅作为讲解组织参考，不作为评测种子（评测种子在根级 `_eval_seeds/`）。

`manifest.yaml` 的 `allowed_use` 必须为 `teaching_organization`，不允许为 `science_fact_evidence`。

### 5.3 `03_multimodal/`（多模态素材）
对应代码侧：
- `VisualPage`/`PageRegion`/`VisualAsset`/`LayoutTrace`（`schemas.py`）。
- `visual` 通道（`configs/rag.yaml` retrieval.channels.visual，协议预留：`enabled: false`，数据未入库，暂未启用）。
- `SceneObject` 绑定（`linked_visual_asset_ids`）。
- `gate.require_visual_text_cross_check=true` 强制图文交叉验证（契约预留；无 visual 证据进入链路时该门禁不生效）。

- `images/`：原始图像，每张必须在 manifest 中登记 `source_id`、`original_uri`、`page_id`。
- `structure_diagrams/`：结构图与标注图（机翼/机体/发动机剖面等），`bbox` 必须对应 `BoundingBox` 字段。
- `scene_objects/`：3D 场景对象绑定，字段对齐 `SceneObject`（`hotspot_id`、`model_node_id`、`model_path`）。
- `cross_checks/`：图文交叉验证说明，`text_cross_check` 字段必须非空，否则 `usable_as_core_evidence=false`。

### 5.4 `04_terms_graph/`（术语图谱素材）
对应代码侧：
- `GraphNode`/`GraphEdge`（`schemas.py`）。
- `graph` 通道（`configs/rag.yaml` retrieval.channels.graph，`max_hops=2`）。
- `configs/terminology.yaml` 的术语来源。

- `terms/`：术语与别名，字段对齐 `GraphNode.aliases`、`GraphNode.canonical_name`。
- `entities/`：实体定义（部件/系统/概念），`node_type` 取值：`component`/`system`/`concept`/`aircraft`。
- `relations/`：关系种子，`relation_type` 建议枚举：
  - `part_of`（部件属于系统）
  - `depends_on`（系统依赖）
  - `derives_from`（技术派生）
  - `parameter_of`（参数属于部件）
  - `compared_with`（对比关系，用于 `06_comparison`）

### 5.5 `90_reference_only/`（参考资料，V1 默认关闭）
- V1 在 `object.yaml` 中 `partition_enable.90_reference_only=false`，不参与入库。
- 预留子目录：`training_materials/`、`maintenance_manuals/`、`standards/`、`case_studies/`、`transformation_notes/`。
- `transformation_notes/`：记录参考资料到科普证据的转化说明，是后续把参考资料派生为 `01_science` 证据的工程入口。

## 6. 入库批次与评测种子目录

### 6.1 `_ingestion_batches/`
对应代码侧：`KnowledgeRepository.start_ingestion_job`/`finish_ingestion_job`、`scripts/ingest_sources.py` 的过程证据。
- 命名规范：`YYYYMMDD_<批次号>_<对象>_<分区>/`，例如 `20260728_001_c919_01_science/`。
- 每个批次目录必须包含：
  - `batch_manifest.yaml`：参与的 manifest 文件列表、入库命令、配置摘要。
  - `ingestion_report.json`：`scripts/ingest_sources.py` 的输出归档。
  - `validation_report.json`：`scripts/validate_knowledge_base.py` 的输出归档。
- 入库批次不放入单个知识对象资料区，集中放在根级 `_ingestion_batches/`。

### 6.2 `_eval_seeds/`
对应代码侧：`configs/evals.yaml`、`src/evaluation/*` 的种子来源。
- `_eval_seeds/README.md` 写明：评测种子是资料侧维护的问题种子，正式可运行评测仍由现有配置、脚本和测试系统执行。
- `_eval_seeds/c919/` 按 `01_science` 的 6 子分区同名命名，便于问题与证据分区对齐：
  - `overview_qa_seeds.yaml`、`structure_qa_seeds.yaml`、`principles_qa_seeds.yaml`、`history_qa_seeds.yaml`、`applications_qa_seeds.yaml`、`comparison_qa_seeds.yaml`。
- 每条种子字段：`question`、`expected_intent_type`（concept_explanation/parameter_fact/comparison/component_scene）、`expected_complexity`（L1-L5）、`expected_evidence_partitions`、`notes`。

## 7. `manifest.yaml` 规范与示例

### 7.1 字段词典（与 `SourceRecord` 对齐）

| manifest 字段 | 对应代码字段 | 必填 | 说明 |
|---|---|---|---|
| `source_id` | `SourceRecord.source_id` | 是 | 全局唯一，建议 `c919-<分区>-<短标题>-<版本>` |
| `source_type` | `SourceRecord.source_type` | 是 | `text`/`pdf`/`image`/`table`/`graph` |
| `title` | `SourceRecord.title` | 是 | 人读友好标题 |
| `authority_level` | `SourceRecord.authority_level` | 是 | `official`/`project_reviewed`/`standard` |
| `review_status` | `SourceRecord.review_status` | 是 | `draft`/`candidate`/`reviewed`/`deprecated` |
| `version` | `SourceRecord.version` | 是 | 资料版本，如 `v1`、`v2` |
| `applicable_aircraft` | `SourceRecord.applicable_aircraft` | 是 | 默认 `[c919]` |
| `allowed_use` | `SourceRecord.metadata.allowed_use` | 是 | 见 7.2 |
| `aircraft` | `TextChunk.aircraft` | 是 | 入库时写入 chunk 元数据 |
| `component` | `TextChunk.component` | 否 | `02_structure_systems` 必填 |
| `concept` | `TextChunk.concept` | 否 | `03_principles` 必填 |
| `knowledge_type` | `TextChunk.knowledge_type` | 是 | 见 7.3 |
| `content_hash` | `SourceRecord.content_hash` | 否 | 入库时由脚本计算 |
| `original_uri` | `SourceRecord.original_uri` | 否 | 原始下载或引用 URI |
| `timeline` | `metadata.timeline` | 否 | 时间敏感资料的里程碑日期 |
| `text_cross_check` | `VisualAsset.text_cross_check` | 是（视觉类） | 图文交叉验证文本 |

### 7.2 `allowed_use` 枚举（固定）
- `science_fact_evidence`：科普事实证据，仅 `01_science` 分区可用。
- `teaching_organization`：教学组织素材，`02_teaching` 专用。
- `visual_aid`：视觉辅助，`03_multimodal/images|structure_diagrams` 使用。
- `scene_object_binding`：场景对象绑定，`03_multimodal/scene_objects` 使用。
- `terminology_graph`：术语图谱素材，`04_terms_graph` 专用。
- `reference_only`：参考资料，`90_reference_only` 专用。
- `evaluation_seed`：评测种子，`_eval_seeds/` 使用（根级，非对象内）。

### 7.3 `knowledge_type` 枚举（与 prompt 资产对齐）
取值参考 `assets/prompts/*/asset.json` 的 `activation_scope`：
- `overview`、`parameter_fact`、`component_role`、`system_explanation`、`principle_explanation`、`milestone_event`、`value_analysis`、`comparison`、`definition`。

## 8. 命名规范

### 8.1 资料文件名
- 格式：`<对象>-<主题>-<日期YYYYMMDD>-<review_status>.<ext>`
- 示例：`c919-wing-structure-20240601-reviewed.md`、`c919-overview-20240601-reviewed.pdf`。
- 机器唯一性由 `manifest.yaml` 的 `source_id` 承载，不强制把完整 `source_id` 塞进文件名。

### 8.2 `source_id` 命名
- 格式：`<对象>-<分区短名>-<短标题>-<版本>`，例如 `c919-science-overview-v1`、`c919-science-wing-v1`。
- 跨对象共享资料（如通用气动原理）不放入单对象目录，应放入根级 `_shared/`（本设计暂不创建 `_shared/`，跨对象资料在 V1 不存在）。

### 8.3 入库批次命名
- 格式：`YYYYMMDD_<批次号3位>_<对象>_<分区>`，例如 `20260728_001_c919_01_science`。

### 8.4 评测种子命名
- 格式：`<分区短名>_qa_seeds.yaml`，例如 `overview_qa_seeds.yaml`。

## 9. 目录红线（禁止事项）

1. `00_inbox/` 不得作为入库来源，不能被引用为科普证据源。
2. `90_reference_only/` 不得直接作为科普证据源；必须经人工转化或审核后派生为 `01_science` 证据，并在 `transformation_notes/` 记录转化说明。
3. 未登记 `manifest.yaml` 的文件不得入库。
4. `review_status` 不得通过移动文件到 `reviewed`/`candidate`/`rejected` 目录表达，必须由 manifest 字段承载。
5. `allowed_use` 不得与分区语义冲突（例：`02_teaching` 不得出现 `science_fact_evidence`）。
6. 运行产物（`data/processed/knowledge.sqlite3`、`langgraph_checkpoints.sqlite3`、`memory.sqlite3`）不得作为权威资料来源。
7. 跨对象资料不得塞入单对象目录；V1 不引入跨对象共享目录。
8. 骨架对象（j20/y20/z20）下不得创建分区目录，避免"空目录即启用"。
9. `03_multimodal` 资料无 `text_cross_check` 不得标记 `usable_as_core_evidence=true`（与 `gate.require_visual_text_cross_check=true` 对齐）。
10. `01_science` 中 `parameter_fact` 类资料必须提供 `original_uri` 或 `metadata.source_statement`（与 `gate.require_parameter_source=true` 对齐）。

## 10. 与项目代码的对应关系

### 10.1 检索通道对应
| `configs/rag.yaml` 通道 | 资料分区 | 代码消费者 |
|---|---|---|
| `keyword` | `01_science` | `knowledge/indexes/keyword_index.py` |
| `table` | `01_science/06_comparison`、`01_overview` 参数表 | `knowledge/indexes/table_index.py` |
| `dense` | `01_science` 全部分区 | `knowledge/indexes/vector_store.py` |
| `parent` | `01_science`（每个 parent 文档） | `knowledge/indexes/parent_index.py` |
| `scene` | `03_multimodal/scene_objects`、`02_structure_systems` | `knowledge/indexes/scene_index.py`、`scene_object_registry.py` |
| `visual` | `03_multimodal` | `knowledge/indexes/visual_page_index.py` |
| `graph` | `04_terms_graph` | `knowledge/indexes/graph_index.py` |

> 通道状态口径：上表仅为「通道 → 资料分区 → 代码消费者」映射，不代表通道已启用。实际启用状态以 `configs/rag.yaml` retrieval.channels 为准：`keyword`/`table`/`dense`/`parent` 为 `enabled: true`；`scene`/`visual`/`graph` 为协议预留（`enabled: false`，数据未入库，暂未启用），即多模态通道为协议预留、未启用。

### 10.2 Schema 字段对应
| manifest 字段 | 代码 schema | 入库路径 |
|---|---|---|
| `source_id` 等 | `SourceRecord` | `KnowledgeRepository.register_source` |
| `parent` 文档 | `ParentDocument` | `TextIngestor.ingest_document` |
| `chunk` 字段 | `TextChunk` | `TextIngestor._prepare_document` |
| `visual` 字段 | `VisualPage`/`VisualAsset`/`LayoutTrace` | `VisualIngestor` |
| `scene` 字段 | `SceneObject` | `SceneIngestor`、`SceneObjectRegistry` |
| `graph` 字段 | `GraphNode`/`GraphEdge` | `GraphIngestor`、`GraphIndex` |

### 10.3 CLI 对应
`scripts/ingest_sources.py` 参数与本设计 manifest 字段一一对应：
- `--source-id` ← manifest `source_id`
- `--title` ← manifest `title`
- `--source-type` ← manifest `source_type`
- `--authority-level` ← manifest `authority_level`
- `--review-status` ← manifest `review_status`
- `--aircraft` ← manifest `aircraft`
- `--component` ← manifest `component`
- `--concept` ← manifest `concept`
- `--project-maintainer` ← `reviewed` 状态必填（`MaintainerAuthorizationError`）

### 10.4 Evidence Gate 对应
`configs/rag.yaml` 的 `gate`：
- `allowed_core_review_status: [reviewed]` ← manifest `review_status=reviewed`
- `min_core_items: 1` ← 每个问题至少 1 条 reviewed 证据
- `require_parameter_source: true` ← `parameter_fact` 类资料必须有 `original_uri`
- `require_visual_text_cross_check: true` ← `03_multimodal` 必须有 `text_cross_check`
