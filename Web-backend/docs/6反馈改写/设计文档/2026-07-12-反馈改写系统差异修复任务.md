## 3. 专项定位与根因

### 3.1 当前骨架

当前仓库已有如下独立组件：

```text
FeedbackEvent
→ FeedbackParser
→ CheckpointStore
→ EvidenceLock
→ RewritePlanner
→ ControlledRewriter
→ DeltaMapper
```

该骨架覆盖了八类反馈意图、来源绑定复制、基础安全回复和候选记忆接口，但没有成为用户可进入的主链路。现有“E2E”测试直接手工创建 checkpoint 并串联函数，不能证明系统运行时真的具备反馈改写能力。

### 3.2 已确认的根因级差异

1. `AgentRuntime`、`AppPipeline`、API schema 与 CLI 没有正式反馈入口；最终答案没有自动保存 checkpoint，反馈状态机不可达。
2. `FACT_CHALLENGE` 和 `SCENE_REBIND` 只返回提示文本或字符串动作，未回到 P3 执行核查检索、场景重绑定和局部修订。
3. 改写后没有由运行时强制进入 P5；即使外部手工调用 P5，当前检查只读取旧 `claim_candidates`，无法发现正文中新插入的事实。
4. `EvidenceLock.validate_rewrite()` 未被改写器调用；它还会放行没有 `evidence_ids` 的新增 claim，并将所有 evidence item 视为可锁定证据。
5. `DeltaMapper` 只比较旧 claim 元数据，不能表达正文句子、删改位置和来源迁移；改写器修改正文时通常仍保留旧 claim 元数据。
6. `EXPAND` 被解析后没有对应改写实现；简化和表格化是固定字符串替换，不能按目标片段、目标维度、来源映射或用户请求完成受控修改。
7. `feedback.max_rewrite_rounds`、允许格式、偏好稳定阈值与安全模式均未配置化；checkpoint 的 `rewrite_round` 没有消费或递增。
8. 单次“太专业了”会立即进入 `MemoryController.process_event()` 并写成 ACTIVE 长期偏好，违背“单次只影响当前回答、稳定多次后才形成候选”的设计。
9. `CheckpointStore` 仅为进程内字典；缺失 checkpoint 直接抛出 `KeyError`，模块级 `save_checkpoint()` 每次创建新 store，属于无状态且不可用的冗余接口。
10. `BargeInController` 仅构造 `FeedbackEvent`，没有停止播报或调用反馈服务；还会写入未定义的 `INTERRUPT` 值。
11. `RunTrace` 预留 `rewrite_log_id`，但没有写入实际 rewrite log、checkpoint、反馈事件、动作路径或最终 answer 的关联关系。
12. `aviation_feedback_rewrite` Prompt 资产处于 active 状态，却没有被正式反馈改写路径消费。

## 4. 目标架构与不可突破边界

### 4.1 目标闭环

```text
初始文本/语音问答
→ P3 EvidencePackage → P4 AnswerEnvelope → P5 CheckReport
→ FINAL_READY：保存 FeedbackCheckpoint

FeedbackRewriteRequest(checkpoint_id, feedback_event)
→ checkpoint 归属/轮数/状态验证
→ FeedbackParser
→ FeedbackDecisionRouter
  ├─ 表达类：EvidenceLock → RewritePlan → ControlledRewriter
  │          → Claim/source 重建 → P5 → FINAL_READY
  ├─ 事实质疑：VerificationQuery → P3 补检索 → EvidenceLock 更新
  │            → 局部改写 → P5 → FINAL_READY
  ├─ 场景重绑定：Scene rebinding → P3 补检索或 ASK_CLARIFICATION
  ├─ 安全反馈：SAFE_RESPONSE
  └─ 偏好反馈：当前会话生效 → 稳定性检查 → P2 候选治理
→ RewriteLog + RunTrace 摘要
```

### 4.2 单一职责

- `FeedbackRewriteService` 是 P6 唯一编排入口；负责读取 checkpoint、调用子模块、驱动动作分流、调用 P3/P5、保存新 checkpoint 和写 trace。
- `FeedbackParser` 只识别反馈语义与目标，不负责记忆写入、事实裁决或检索。
- `CheckpointStore` 只保存、读取、校验和推进 checkpoint，不负责业务决策。
- `EvidenceLock` 只定义可用证据和允许变化；任何草稿通过它验证前不得成为最终答案。
- `ControlledRewriter` 只根据 `RewritePlan` 和锁定/补充证据生成草稿，不自行决定回退动作。
- P3 仍是唯一检索与 evidence package 构建者；P5 仍是唯一质量裁决者；P2 仍是唯一长期记忆治理者。
- 语音模块只把打断标准化为反馈事件，并先停止旧播报；不得复制第二套反馈改写逻辑。

### 4.3 事实、安全和记忆边界

- 航空事实只能来自当前 evidence lock 中 `reviewed` 且 `usable_as_core_evidence=true` 的证据，或 FACT_CHALLENGE/SCENE_REBIND 后由 P3 新生成并通过门控的证据。
- 用户反馈、记忆、Prompt、模型常识和视觉直觉只能提供改写信号或检索线索，不得直接构成事实 claim。
- 新增或改写后的每个事实 claim 必须有可用 evidence ID、可追溯文本 span 和 `source_binding`；无法绑定时必须删除或降级为不确定性说明。
- `SAFE_RESPONSE` 不得给出可执行维修、拆卸、改装、故障处置或规避步骤；可保留不含危险操作的科普原理与安全边界。
- 单次偏好只更新 `session_preference`/事件日志；跨独立反馈事件达到配置阈值且通过授权、隐私和冲突检查后，才向 P2 提交长期记忆候选。

### 4.4 外部兼容和非目标

- 保持既有 `ActionDecision` 值：`PASS`、`REWRITE_ONLY`、`RETRIEVE_MORE`、`ASK_CLARIFICATION`、`HUMAN_REVIEW`、`SAFE_RESPONSE`、`MEMORY_CANDIDATE`、`STOP`。
- 不修改现有文本问答请求/响应的字段和语义；新增 `FeedbackRewriteRequest`/`FeedbackRewriteResponse` 与对应 CLI 适配，不复用文本问答 request 伪装反馈。
- 保持 `AnswerEnvelope` 顶层字段可反序列化；内部可新增兼容字段，但不创建第二套 answer contract。
- checkpoint 可继续采用本地轻量持久化或明确生命周期的应用内 store；本专项不接入真实生产数据库、队列、人工审核系统、真实模型或新的 LangGraph/LangChain/Ragas/DeepEval 等大型依赖。
- 本专项不重做 P3 检索算法、不修改 P4 初始生成策略、不重做 P5 评分算法；只通过正式接口向这三个阶段发出已有契约允许的请求和输入。

## 5. 核心契约

### 5.1 `FeedbackRewriteRequest`

必须包含：

- `run_id`
- `checkpoint_id`
- `feedback_event`
- `user_id`
- `session_id`
- `source`（`text` 或 `voice`）

校验规则：checkpoint 必须属于同一 run；如 checkpoint 带用户/会话绑定，request 必须匹配；请求不能携带用户自定义 evidence 或直接替换上一轮答案。

### 5.2 `FeedbackParseResult`

必须包含：

- `feedback_intent`
- `normalized_feedback`
- `target_span`（全文、句子、术语、来源或 display block）
- `target_dimension`（事实、表达、长度、格式、语气、场景、安全）
- `confidence`
- `verification_queries`
- `requested_format`
- `preference_signal`
- `safety_sensitive`

除 canonical 八类意图外，`LEVEL_DOWN`、`DETAIL_PRINCIPLE`、`CONCLUSION_ONLY` 等只作为表达策略字段，不得新增与全局动作枚举竞争的 intent 值。

### 5.3 `FeedbackCheckpoint`

必须保存：

- `checkpoint_id`、`run_id`、`answer_id`、`created_at`、`rewrite_round`
- `previous_answer_envelope`、`evidence_package`、`self_check_report`
- `scene_state`、`source_binding`、`memory_context_id`
- 可重建的 prompt/retrieval provenance

读取结果必须区分 `FOUND`、`NOT_FOUND`、`RUN_MISMATCH`、`EXPIRED` 和 `ROUND_LIMIT`。禁止把这些状态映射为未经解释的 `KeyError`。

### 5.4 `RewritePlan` 与 `RewriteLog`

`RewritePlan` 至少包含：

- `feedback_intent`、`target_span`、`target_dimension`
- `action_decision`
- `rewrite_actions`
- `verification_queries` 或 `retrieval_request`
- `preserved_source_binding`
- `new_uncertainty_notes`
- `memory_update_candidate`

`RewriteLog` 至少包含：

- `run_id`、`checkpoint_id`、`feedback_event_id`
- `feedback_intent`、`rewrite_action`、`action_decision`
- `changed_claims`、`removed_claims`、`added_claims`
- `preserved_source_binding`、`self_check_result`
- `rewrite_round`、`latency_ms` 和脱敏的 `user_acceptance_signal`

### 5.5 `DeltaMap` 和 claim/source 不变量

- Delta 必须以答案文本 span/claim 为最小粒度，区分 `preserved`、`rewritten`、`removed`、`added`、`hedged`。
- 每个 delta 条目必须记录旧 span、新 span、claim ID、证据 ID 列表和变更原因。
- `added`/`rewritten` 事实 claim 必须由当前 evidence lock 显式支持；空 evidence ID、不可用 evidence 或无法迁移的 binding 均为失败关闭。
- `source_binding` 是 claim 到 evidence 的 canonical 映射；`evidence_refs` 必须等于所有有效 binding 的去重并集。

## 7. 分工作包验收场景

| 编号 | 场景 | 必须结果 |
| --- | --- | --- |
| FR-01 | 初始问答到 `FINAL_READY` | 自动保存可读取、可归属验证的 checkpoint。 |
| FR-02 | checkpoint 缺失、过期或 run 不匹配 | 返回结构化澄清/保守降级，trace 有原因码，无 `KeyError`。 |
| FR-03 | “太专业了，简单点” | 只改表达，保留 claim/evidence binding，进入 P5，单次不入 ACTIVE 长期记忆。 |
| FR-04 | “再短一点”且原答案有安全提醒 | 压缩非必要说明但保留安全提醒和关键限定。 |
| FR-05 | “详细解释原理” | 仅从当前锁定证据展开；无可用支持时发起补检索或说明不能补充。 |
| FR-06 | “用表格对比” | 按证据支持的维度迁移引用；未覆盖维度显示“资料未覆盖”。 |
| FR-07 | “你说错了” | 输出核查查询，回 P3 取证；只修改被新证据推翻或补充的局部 claim。 |
| FR-08 | “我说的是旁边那个部件”且对象唯一 | 重绑 scene object，补检索相关资料，再改写并自检。 |
| FR-09 | 场景指代仍不明确 | `ASK_CLARIFICATION`，不继续生成部件事实。 |
| FR-10 | 新增事实 claim 没有 evidence IDs | EvidenceLock 拒绝，P5 也不得 PASS。 |
| FR-11 | 正文修改但未更新 claim metadata | claim/span 重建发现变化，delta 与来源迁移完整。 |
| FR-12 | 连续反馈到最大轮数 | `STOP` 或澄清，说明限制；不无限重写。 |
| FR-13 | 同一偏好仅一次 | 仅 session/event 记录，不创建 ACTIVE 长期 memory。 |
| FR-14 | 跨独立会话重复稳定偏好达到阈值 | 生成长期候选并经 P2 接受后写入。 |
| FR-15 | 语音播报中“停一下，讲简单点” | 停止旧 TTS，产生 canonical feedback event，改写走 F2 服务。 |
| FR-16 | 语音播报中“不是这个” | 停止旧 TTS，进入场景重绑定或澄清，而不是写入 `INTERRUPT`。 |
| FR-17 | 反馈改写完成 | `RunTrace` 含 checkpoint、feedback、rewrite log、P5 结果与 final answer 的脱敏关联。 |

删除动作只能在 F8 且满足替代路径已被集成测试覆盖后执行：

- `src/feedback/checkpoint_store.py` 中无状态模块级 `save_checkpoint()` 包装函数。
- 被 `FeedbackRewriteService` 完全替代的 `parse_feedback()`、`plan_rewrite()`、`rewrite_answer()` 等模块级手工拼装包装函数。
- 只验证来源字典复制、不通过正式 runtime 的旧“E2E”测试路径。
- `BargeInController` 中产生非 canonical `INTERRUPT` 的分支。
- 没有调用方的反馈 prompt、兼容方法、重复动作分流或死配置。

删除前必须执行 `rg` 覆盖 `src`、`tests`、`scripts`、`configs` 和 `docs`，并在提交前通过目标测试与全量测试。不得保留“新 service + 旧函数式主链”双轨实现。

## 9. 测试与验收原则

1. 每个行为改动先写红测，并确认它在替代实现前失败。
2. 单元测试验证 parser、policy、checkpoint、evidence lock、claim rebuild、delta 和偏好稳定性等纯逻辑。
3. 集成测试必须从 `AgentRuntime` 或 `AppPipeline` 开始，禁止仅手工串联 feedback helper 冒充端到端。
4. E2E 必须覆盖文本反馈、语音 barge-in、事实核查、场景重绑定、P5 拦截、P2 治理、CLI/API 和 trace。
5. 不得以 `status=ok`、非空答案、来源字典相等或绿测数量代替事实安全验证。
6. 删除旧测试前必须有更强的公共行为测试替代，且不得降低断言强度。
7. 所有离线验证使用 mock provider、假检索或本地 fixture；不得读取密钥、生产数据库或真实外部服务。

## 10. 风险、回滚与停止条件

| 风险 | 控制措施 |
| --- | --- |
| P6 接线破坏既有文本问答 | F0 冻结文本问答兼容测试；新增反馈入口，不改变已有 request 的语义。 |
| P3/P5 接口不足以承载核查/复检 | 先在 F1/F5 检查当前契约；若需破坏性跨阶段改动，记录“待确认”并停止。 |
| 轻量 checkpoint 重启后丢失 | 在 F1 明确保存生命周期与降级行为；不得把临时内存存储描述为生产持久化。 |
| 模型改写引入幻觉 | EvidenceLock 强制验证、claim 重建、P5 复检；无绑定内容失败关闭。 |
| 偏好被偶然反馈污染 | 配置稳定阈值、按用户/会话分组、只在阈值后提交 P2。 |
| 语音重复实现反馈逻辑 | 只允许语音适配层创建 canonical request，所有决策复用 F2 service。 |
| 清理误删兼容能力 | 先迁移调用方，`rg` 证明零引用，再删；每工作包独立提交和验证。 |

除 `AGENTS.md` 的停止条件外，发生以下情况必须停止并将“待确认”写入 `docs/项目总控/STATUS.md`：

1. 需要新增大型工作流框架、数据库、队列或真实 Provider。
2. P3 或 P5 正式接口无法支持 `verification_queries`、补充 evidence 或改写后输入，且补齐会改变其外部契约。
3. 需要把 `HUMAN_REVIEW` 接到真实人员、生产服务或外部系统。
4. 现有公开 CLI/API 无法以新增方式承载 feedback request。
5. 任何实现会让用户反馈、记忆或 Prompt 资产成为航空事实来源。

## 11. 每工作包 STATUS 记录要求

每完成一个 F 工作包，必须在 `docs/项目总控/STATUS.md` 记录：

- 工作包编号与名称
- 已完成任务与未完成事项
- 修改、新增、删除文件清单
- 执行的红测、目标测试、回归测试与结果
- checkpoint/trace/安全/偏好治理验证结果
- `harness.md` 违反检查与 dead-code 搜索结果
- 是否存在待确认项
- 是否可以进入下一工作包

## 12. 专项完成定义

仅当全部条件同时满足，才可声明反馈改写专项完成：

- 用户能通过正式 runtime、API/CLI 或语音入口对已完成问答提交反馈。
- 每个反馈都有可校验 checkpoint、明确动作、trace 与最终答复关联。
- 表达类改写不新增事实、保留必要引用与安全说明，且通过 P5。
- 事实质疑和场景重绑定真正返回 P3，使用新证据后再做局部修订。
- 任意新增/改写事实都通过 evidence lock、claim/source 重建与 P5；正文变化不能绕过检查。
- 缺失 checkpoint、对象不明、安全请求和轮次上限均有可解释降级。
- 单次反馈不直接写入 ACTIVE 长期记忆，稳定偏好只经 P2 治理写入。
- 语音打断先停止旧播报，再复用同一 P6 闭环。
- `aviation_feedback_rewrite` Prompt 资产只通过正式路径使用，或在无调用时被删除；不存在死资产。
- 不存在无状态 checkpoint wrapper、手工拼装主路径、重复决策或无引用死代码。
- 专项、全量、smoke、trace、compile 与 deployment 验证均有新鲜通过证据，且总控/API/评测/STATUS 文档与实现一致。
