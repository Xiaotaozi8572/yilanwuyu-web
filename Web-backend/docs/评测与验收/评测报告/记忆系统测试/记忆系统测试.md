## 5. 外部模型调用说明

本轮 T4 目标是记忆读取、治理、并行和故障边界；现有 T4 自动化不需要调用外部 LLM。当前进程未检测到 `DEEPSEEK_API_KEY`，因此没有发起外部模型请求，也没有用 mock LLM 冒充真实 LLM 结果。

测试中的 fake gRPC、fixture profile 和 deterministic embedding 仅用于验证记忆服务协议、超时、治理和并行时序；它们不构成 LLM 质量结果。若后续需要测“记忆上下文对真实回答生成的影响”，应在配置真实 API 密钥后，通过正式 `AppPipeline` 入口调用真实 provider，并单独记录 provider、model、fallback 和耗时。

## 7. 待确认与建议

1. 若要严格兑现方案中“100% 读取 P100 ≤150ms”，应在隔离的非生产环境对真实 Java memory service 运行固定样本量的延迟采样，并输出 p50/p95/p99/p100；本轮只验证硬截止逻辑。
2. 若要严格给出“并行 ≤ 串行 60%”结论，应补充记录串行/并行 wall-clock，并在相同数据、相同模型预热状态下计算比例；本轮已验证重叠和隔离，但未伪造比例。
3. `java-down` 和熔断行为当前是本地 fake gRPC/状态机测试；真实 Java 服务故障演练需另行授权并使用脱敏、隔离环境。
4. 不建议为了通过 T4 评测改动业务逻辑；当前核心自动化门禁已通过，未量化项应作为独立性能/部署验收处理。
