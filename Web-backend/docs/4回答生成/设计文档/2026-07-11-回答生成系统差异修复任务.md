## 3. 专项定位

### 3.1 为什么需要专项重构

当前代码已经形成以下模块骨架：

```text
QueryObject / SceneState / MemoryContext
→ EvidencePackage
→ AnswerType
→ EvidenceSketch
→ GenerationPlan
→ AnswerEnvelope
→ CitationBinder / DisplayBlockBuilder
→ SelfCheckService
→ ActionDecision
```

该骨架与设计文档的模块分层基本一致，但真实运行语义仍停留在规则化 MVP，存在以下根因级问题：

1. `AgentRuntime` 未把 `ModelClient`、`ModelOptions` 和模型启用策略注入回答生成主链，Prompt 已组装但不参与正文生成。
2. `AnswerEnvelope`、claim、来源绑定和展示块大量使用无约束字典，结构化输出只校验少量顶层字段。
3. 引用绑定和 P5 自检只确认 evidence ID 是否存在，不确认 claim 是否被证据语义支持。
4. 空 `claim_candidates` 会被视为零 unsupported claim，从而得到满分事实落地结果。
5. 规则生成器只使用第一条事实，`relations`、冲突证据、视觉线索和多证据综合没有进入生成过程。
6. 六类回答虽然存在枚举，但路由优先级、澄清条件和参数证据判断存在错误。
7. 安全回答可能把未命中关键词的可执行步骤作为“背景”重新附加到正文。
8. `RETRIEVE_MORE` 只重复原检索计划，没有生成新查询、证据类型要求或权威等级要求。
9. generation、provider、voice 等配置存在“YAML 已声明但运行时未消费”的双轨状态。
10. 多个模块级包装函数、重复安全回答正文、未读取字段和无引用 Prompt 数据类增加了维护成本。

### 3.2 专项阶段命名

本专项使用 `G0` 至 `G8` 作为维护工作包编号，不创建新的历史 P 阶段，也不覆盖已有 P0 至 P8 的验收记录。

每个 G 工作包必须按其涉及模块分别遵守原 P 阶段 harness。例如：

- 核心契约遵守 P0 边界。
- 输入与 Prompt 路由遵守 P1 边界。
- 记忆只读边界遵守 P2 边界。
- 检索补充指令遵守 P3 边界。
- 回答生成遵守 P4 边界。
- 自我检查遵守 P5 边界。
- 反馈兼容遵守 P6 边界。
- 语音投影遵守 P7 边界。
- 评测、追踪与部署验证遵守 P8 边界。

任何跨层工作必须拆成先低阶段、后高阶段的独立提交，不允许在一个提交中绕过原阶段边界完成大爆炸式重写。

### 3.3 实施澄清（不改变功能范围）

以下约束用于消除实施计划中的歧义，不扩大本专项已经批准的功能范围：

1. generation、model、retrieval、self-check、voice、streaming 六类横跨模块的 settings 集中在 `core/runtime_settings.py`；Voice 与 Safety 配置不得放入 generation 模块。
2. G3 必须原子接通 `AppPipeline` 的生成主路径；G5 再替换 recovery loop，不得在 G3 提前并行保留两套运行时主链。
3. G3 只产生 display intents；`DisplayBlock` 仅在 P5 自检通过并达到 `FINAL_READY` 后物化，以满足“展示不创造事实”的硬原则。
4. `GenerationRequest` 保留 `prompt_bundle` 字段。正常运行必须在 plan/outline 完成后组装 bundle；外部 supplied bundle 只允许用于严格 replay，不能成为另一条普通运行入口。
5. G1 建立 `core.answer_contracts.AnswerEnvelope` canonical。旧 `core.contracts.AnswerEnvelope` 在增量迁移期间只指向显式 `LegacyAnswerPayload`；G7 在生产与测试调用清零后才能改为 canonical re-export，确保每个中间提交保持绿色。

若上述澄清被认为构成对已批准范围的实质架构变更，必须按停止条件暂停并记录待确认；不得静默采用两套解释。

## 4. 核心实施原则

### 4.1 契约优先

先用兼容性测试冻结外部接口，再修改内部实现。专项完成后必须保持：

- `TextQueryRequest` 的字段、构造方式和基础验证行为不变。
- `TextQueryResponse.to_dict()` 顶层键继续为：
  - `run_id`
  - `status`
  - `answer`
  - `action_decision`
  - `trace`
  - `error`
- `answer` JSON 保留当前既有字段名；新增字段只能采用向后兼容的附加方式。
- 六类 `answer_type` 字符串值不变。
- CLI 参数、JSON 输出结构、成功和失败退出码不变。
- 已存在的 trace 字段不得删除或改变原义；新 trace 信息使用新增字段。

### 4.2 证据优先

- `EvidencePackage` 是航空事实唯一来源。
- Prompt、记忆、用户反馈和模型常识不得成为事实证据。
- P4 只能提出 claim 和候选来源绑定；P5 才能确认支持状态。
- 参数、型号、安全和高风险 claim 必须经过结构化证据类型、来源审核状态和权威等级硬门控。
- 冲突证据必须保留双方、差异和限定条件，生成模型不得自行选定一个未经验证的版本。

### 4.3 失败关闭

出现以下情况时，不得输出确定事实：

- 非澄清、非安全答案正文含事实，但 claim 缺失或为空。
- claim 找不到可用来源绑定。
- claim 与来源语义不一致。
- 参数值无法在权威、结构化证据中精确找到。
- 视觉引用缺少合法对象、bbox 或 layout trace。
- 安全检查发现可执行维修、拆卸、改装、故障处置或飞行操作内容。
- 结构化输出缺字段、类型不符或交叉不变量失败。
- 补检索后检索计划和证据指纹均未发生变化。

失败后只能进入显式 fallback、澄清、安全回复、人工复核或停止动作，并在 trace 中记录原因。

### 4.4 单一职责和单一事实源

- Provider 选择只允许存在于应用组合根或模型工厂。
- 模型 fallback 决策只允许存在一处。
- 安全回复正文只允许由一个构造器生成。
- claim 类型只允许定义一套 canonical contract。
- 来源支持状态只允许由 P5 验证器写入。
- DisplayBlock 和 spoken answer 只能投影已经存在于最终 envelope 的内容，不能重新生成事实。
- 配置值只能有一个运行时来源，禁止 YAML 与类默认值长期并存且含义不一致。

### 4.5 测试优先和小步提交

- 每项行为变化先写失败测试，再做最小实现。
- 每个 G 工作包必须形成独立、可拒绝、可回滚的评审单元。
- 每个工作包完成时运行目标测试、前序回归和规定的集成测试。
- 所有历史绿色测试在重构后仍需通过；需要替换的测试必须先建立更强的公共行为测试。
- 不得为了消除失败而删除测试或降低断言强度。

### 4.6 冗余和死代码治理

代码清理遵守以下顺序：

1. 证明目标代码没有运行时、测试、脚本、配置反序列化或仓库外兼容用途。
2. 建立或确认替代接口。
3. 迁移全部调用方和测试。
4. 使用 `rg` 确认旧符号只剩定义或零引用。
5. 删除旧代码、旧测试和失效配置。
6. 运行 compile、目标测试和全量测试。

禁止长期保留“新实现 + 旧实现 + 双向适配器”。专项只允许保留应用边缘的外部兼容适配。

## 5. 目标架构

### 5.1 总体数据流

```text
TextQueryRequest
→ QueryObject / SceneState / MemoryContext
→ 输入安全预判
→ 初始 RetrievalPlan / EvidencePackage
→ AnswerGenerationPipeline
    → AnswerTypeRouter
    → EvidenceSketchBuilder
    → GenerationPlanner
    → AnswerOutlineBuilder
    → PromptRuntime
    → ModelDraftGenerator 或 DeterministicFallbackGenerator
    → ClaimNormalizer
    → CitationBinder（只建立候选绑定）
    → DisplayBlockBuilder
    → GenerationTraceBuilder
→ SelfCheckPipeline
    → 结构完整性检查
    → 独立正文 claim 抽取
    → claim—evidence 语义验证
    → 参数和权威来源检查
    → 场景、多模态和冲突检查
    → 记忆与 Prompt 边界检查
    → 安全硬门控
    → DecisionRouter
→ PASS / REWRITE_ONLY / RETRIEVE_MORE / ASK_CLARIFICATION / HUMAN_REVIEW / SAFE_RESPONSE / STOP
→ TextQueryResponse 兼容序列化
→ SpokenAnswerBuilder
→ TTS
```

### 5.2 计划新增的内部核心类型

#### `GenerationRequest`

统一承载：

- `query_object`
- `scene_state`
- `memory_context`
- `evidence_package`
- `prompt_bundle`
- `generation_settings`
- `run_id`
- `retrieve_round`
- `rewrite_round`

#### `ClaimCandidate`

必须包含：

- `claim_id`
- `text`
- `claim_type`
- `risk_level`
- `required_evidence_type`
- `asserted_evidence_ids`
- `source_origin`

#### `SourceBinding`

必须包含：

- `claim_id`
- `evidence_ids`
- `binding_status`
- `qualification_notes`

`binding_status` 在 P4 阶段只能表示候选、缺失或无效，不得直接表示语义 supported。

#### `AnswerPlan`

必须包含：

- 回答目标
- 必须覆盖的知识点
- 禁止生成的内容
- 证据使用顺序
- 各目标 claim 所需证据类型
- 最低来源权威等级
- 是否需要视觉指引
- 是否需要安全模板
- 缺证处理方式

#### `AnswerOutline`

按回答类型定义正文段落、每段目标 claim、候选证据和展示策略。它必须是真正被 drafting 使用的结构，而不是 trace 中的步骤标签。

#### `ClaimSupport`

必须表达：

- `supported`
- `partially_supported`
- `unsupported`
- `contradicted`

并包含每条 evidence verdict 和 reason code。

#### `RetrievalDirective`

必须包含：

- `reason_codes`
- `missing_claim_ids`
- `query_variants`
- `required_evidence_types`
- `filter_overrides`
- `minimum_authority`
- `exclude_evidence_ids`
- `retrieve_round`

#### `SpokenAnswer`

必须包含：

- `text`
- `source_answer_id`
- `included_claim_ids`
- `action_decision`

### 5.3 关键服务边界

- `AnswerGenerationPipeline.generate(request) -> AnswerEnvelope`
- `ModelRuntime.complete_structured(messages, parser, options) -> ModelCallResult`
- `SemanticEvidenceVerifier.verify(claim, evidence, policy) -> ClaimSupport`
- `SelfCheckService.check(answer, evidence, scene, memory, prompt, loop_state) -> CheckReport`
- `refine_retrieval_plan(previous, directive) -> RetrievalPlan`
- `merge_evidence_packages(previous, additional) -> EvidencePackage`
- `SpokenAnswerBuilder.build(envelope, decision, config) -> SpokenAnswer`

  - provider enable/fallback/retry/timeout/model alias
  - voice duration、阈值和术语配置
- 配置缺失或类型错误时启动失败，不在业务代码中偷偷回落到不同默认值。

完成标准：

- 内部生成和自检不再依赖无结构字典。
- 外部兼容测试全部通过。
- 所有声明的 generation 配置均能找到运行时消费者。

### 7.3 G2：路由、证据草图、计划与大纲

#### G2.1 配置化六类路由策略

任务：

- 将路由拆成两个职责明确的步骤：`QueryUnderstandingService` 只提取规范化文本、目标对象、比较/参数/安全等意图信号；`AnswerTypeRouter` 结合意图信号、scene ambiguity 和 evidence gate 形成唯一最终 `AnswerRoute`。
- 六类最终类型只能由 `AnswerTypeRouter` 写入；禁止 QueryUnderstanding 和 generation 各自维护一套互相竞争的关键词优先级。
- 建立 `AnswerRoutePolicy`，为六类回答定义优先级、模板、证据类型、权威要求、缺证行为、展示策略和安全策略。
- 默认优先级：
  1. clarification
  2. operation_safety
  3. comparison
  4. parameter_fact
  5. component_scene
  6. concept_explanation
- 修复输入关键词优先级，确保比较意图不会被部件词提前截获。
- `needs_clarification=True` 必须形成禁止确定回答的计划。
- `AnswerTypeRouter` 必须实际消费 evidence gate 和 scene ambiguity，而不是保留未使用参数。

#### G2.2 完整构建 EvidenceSketch

任务：

- 构建 facts、relations、visual clues、missing points、conflicts 和 generation boundary。
- 每条事实保留 evidence ID、source ID、对象、证据类型、review status、authority、限定条件和适用范围。
- 只允许 reviewed 且 `usable_as_core_evidence=true` 的证据进入事实候选。
- 对视觉证据要求 text cross-check 和 layout 信息。
- 冲突证据保留不同值、各自来源和冲突原因。
- 对 evidence 数量过多执行确定性压缩，压缩结果不得改写数值和限定条件。

#### G2.3 实现 AnswerPlan

任务：

- 根据 route、query、scene、memory boundary 和 sketch 生成实际计划。
- 把知识点、禁止内容、证据顺序、目标 claims、视觉要求、安全要求和缺证策略写入 plan。
- 参数问题不得使用“文本中出现任意数字”作为证据判断。
- comparison 必须按同一维度为双方对象分配证据；缺少一侧时显式标记资料未覆盖。
- conflict 计划只能生成限定表达，不能选边。

#### G2.4 实现 AnswerOutline

任务：

- 为每个段落定义目的、目标 claim、候选证据、展示块和最大长度。
- 确保 outline 被 drafting 消费并在 trace 中记录 outline ID。
- 不允许仅把 `steps=["outline", ...]` 当作已经执行大纲阶段。

完成标准：

- 六类路由回归全部通过。
- 多证据、冲突、视觉、缺证和参数权威测试通过。
- plan 和 outline 都有独立单元测试和至少一个主链集成测试。

### 7.4 G3：模型主链与显式 fallback

#### G3.1 建立应用级 ModelRuntime

任务：

- 在应用组合根根据配置创建 ModelClient、ModelOptions 和 parser。
- `AgentRuntime` 不直接选择 Provider。
- `DeepSeekModelClient`、MockModelClient 和未来 Provider 通过同一接口调用。
- 真实密钥缺失、Provider disabled、model ID 未配置时不得访问网络。

#### G3.2 重构生成流水线

任务：

- 建立 `AnswerGenerationPipeline`，按 route → sketch → plan → outline → prompt → draft → claim normalization → candidate binding → display → trace 顺序执行。
- 将模型生成设为配置允许时的主路径。
- Prompt 必须注入 query、scene、reviewed evidence、memory 摘要、plan、outline、generation boundary 和完整输出契约。
- Prompt 注入顺序遵守 harness，RAG 证据和系统事实边界优先于记忆和 Prompt 资产。

#### G3.3 拆分确定性 fallback

任务：

- 将规则生成器独立为 `DeterministicFallbackGenerator`。
- fallback 只能在配置允许且原因属于许可集合时执行。
- fallback 不得假装模型调用成功。
- trace 记录 provider、model alias、request ID、latency、retry count、error code、fallback reason 和配置版本。
- fallback 仍必须产生完整 typed envelope 并进入 P5。

#### G3.4 消除双轨开关

任务：

- 删除调用方手动传入的 `use_model` 布尔开关。
- 删除重复的 fallback 状态字段或使其成为单一决策源的一部分。
- `ModelOptions.fallback_enabled`、Provider config 和 trace 中 fallback 状态必须来自同一个运行时决策。

完成标准：

- AppPipeline 主链能够使用 MockModelClient 生成结构化答案。
- 模型消息与 Prompt bundle 完全一致。
- 无效模型输出按策略 fail closed 或 fallback，并产生可审计 trace。
- 默认测试不访问真实外部服务。

### 7.5 G4：claim、引用、自检与安全硬门控

#### G4.1 明确 P4 与 P5 的引用职责

任务：

- P4 CitationBinder 只验证 evidence ID 存在、证据可用和绑定格式合法，状态命名为 candidate/invalid/missing。
- 删除 P4 对语义 supported 的提前宣判。
- P5 独占 supported/partially_supported/unsupported/contradicted 最终状态。

#### G4.2 独立正文 claim 完整性检查

任务：

- P5 从 `short_answer` 和 `main_answer` 独立抽取最小事实 claim。
- 将正文抽取结果与模型声明的 claim 列表对齐。
- 正文存在事实而声明列表为空时 fail closed。
- 声明 claim 未出现在正文、正文 claim 未声明或 claim span 不一致时记录结构问题。

#### G4.3 实现语义来源验证

任务：

- 建立 `SemanticEvidenceVerifier` 协议。
- 同时检查语义蕴含、限定条件、对象一致、required evidence type、review status 和 authority level。
- 普通 claim 可使用确定性规则与受约束模型 judge 组合。
- 参数、安全和高风险 claim 必须先通过规则硬门控，模型 judge 不能覆盖硬失败。
- 保存 evidence verdict 和 reason code，禁止只保存总分。

#### G4.4 参数与数值验证

任务：

- 从 claim 提取数值、单位、对象和参数名。
- 在结构化或权威证据中精确匹配数值和单位。
- 区分型号编号、年份、数量、范围和目标参数。
- 多来源数值冲突时进入 contradicted 或 uncertainty，不选择一个值强答。

#### G4.5 集中安全策略

任务：

- 建立单一安全分类器和安全回答构造器。
- 安全三道门：输入预判、生成约束、P5 发布前硬检查。
- 安全回答构造器禁止拼接原始操作步骤证据。
- 安全检查优先级高于循环上限和普通 unsupported claim。
- 安全规则、模板和阈值由配置加载，不再散落硬编码 marker。

#### G4.6 修复决策路由

任务：

- 决策路由实际使用 factual、scene 和 risk thresholds。
- check report 不完整时 fail closed。
- multimodal、conflict、boundary 和 safety issue 都必须有明确动作。
- 空 claim 不得自动获得 factual grounding 1.0。

完成标准：

- 空 claims、语义假引用、参数误判和安全步骤泄漏四类关键反例全部被拦截。
- 每个关键 claim 有最终支持状态、证据 verdict 和 reason code。
- 安全回复只有单一实现。

### 7.6 G5：Runtime 回退闭环与 trace

#### G5.1 注入统一 GenerationService

任务：

- `AgentRuntime` 只负责准备上下文、调用 GenerationService、自检和动作循环。
- 删除 Runtime 对 generation 模块级函数的硬编码串联。
- `AppPipeline` 作为组合根注入 retrieval、generation、self-check、memory 和 settings。
- 消除 AppPipeline 与 Runtime 对同一控制器的重复所有权。

#### G5.2 实现有效 RETRIEVE_MORE

任务：

- P5 生成 typed `RetrievalDirective`。
- P3 使用 directive 改写 query variants、evidence type、authority、filters、exclude IDs 和 budget。
- 新旧 EvidencePackage 通过确定性规则合并并重新过 gate。
- 重新构建 sketch、plan、outline 和 draft。
- 对前后检索计划和证据 ID 计算指纹；无变化时立即停止空转。
- `retrieve_round` 和 `rewrite_round` 独立计数。

#### G5.3 修复 REWRITE_ONLY

任务：

- 根据 claim span 或结构化段落真正修改正文。
- 删除 claim metadata 的同时必须删除或改写正文对应内容。
- 改写后重新进行 claim 抽取、来源验证和安全检查。
- 保留受支持事实和来源，不得新增事实。

#### G5.4 收口终态

任务：

- 所有可发布回答必须经历 `ANSWER_DRAFTED → SELF_CHECKED → FINAL_READY`。
- 未知动作、未实现动作和 `HUMAN_REVIEW` 不得返回原 draft。
- loop limit 后只能输出保守澄清、人工复核或 STOP。
- 错误响应同步 action、trace 状态和错误审计，避免同一错误重复追加。

#### G5.5 完整 Generation Trace

至少记录：

- route policy 和版本
- plan ID、outline ID
- evidence IDs、conflict IDs
- claim candidate bindings 和最终支持状态
- provider、model alias、request ID、latency、retry、fallback
- retrieve/rewrite round
- action reason
- settings snapshot version

禁止记录完整 Prompt、密钥、原始私人记忆或原始音频。

完成标准：

- RETRIEVE_MORE 第二轮有可观察的计划变化。
- REWRITE_ONLY 不再残留 unsupported 正文。
- 所有终态和循环路径有集成测试。

### 7.7 G6：多模态、展示和语音投影

#### G6.1 完整 visual references

任务：

- 将 reviewed visual evidence 的 evidence ID、page、bbox、layout trace、scene object 和 text cross-check 写入 typed visual reference。
- visual ref 不合法时不得进入答案。
- 图文冲突触发澄清、补检索或降级，不得强行解释。

#### G6.2 重构 DisplayBlockBuilder

任务：

- 建立 typed conclusion、explain、source、scene、quiz 和 follow-up block。
- source block 提供客户端可读的 source ID、标题、页码、authority 和 evidence IDs，而不是只有内部 evidence ID。
- scene block 支持 component、highlight、camera hint 和 next hotspot。
- display block 只能引用 envelope 已有文本和证据，不得创造新 claim。

#### G6.3 建立 SpokenAnswerBuilder

任务：

- 从已到 `FINAL_READY` 的 envelope 确定性投影 spoken answer。
- 默认结构为一句结论、两至三句已支持解释和一个可选追问。
- 记录 included claim IDs 和 source answer ID。
- 如果未来使用模型改写 spoken text，改写结果必须重新进入 P5。

#### G6.4 收紧 Voice 边界

只有同时满足以下条件才可送 TTS：

- response status 为 ok。
- 主链状态为 `FINAL_READY`。
- action 属于允许播报集合。
- envelope 强类型校验通过。

同时完成：

- 透传 user ID、session ID 和 run ID。
- pipeline error、STOP 和未决人工复核不得播报为确定事实。
- voice 时长、阈值、Provider 和术语配置从配置加载。

完成标准：

- 视觉来源卡片可由最终响应独立渲染。
- spoken answer 不新增或改变 claim。
- Voice 不再直接无条件读取任意 ok 响应的 short answer。

## 9. 测试和验收原则

### 9.1 测试层次

1. Unit：纯类型、路由、sketch、plan、outline、parser、verifier、policy 和 builder。
2. Integration：answer pipeline、self-check loop、app loop、feedback/checkpoint 和 voice loop。
3. E2E：CLI subprocess、文本可信回答、语音可信回答、反馈改写。
4. Evaluation：固定缺陷回归集、smoke suite、trace 审计和部署验证。

### 9.2 每工作包测试门

每个工作包必须依次通过：

1. 新增红测按预期失败。
2. 最小实现后目标测试通过。
3. 前序工作包回归测试通过。
4. 涉及主链时，相关集成测试通过。
5. 工作包结束时运行项目规定的扩大回归集。

### 9.3 不允许的测试处理

- 不得删除失败测试以完成阶段。
- 不得把严格 equality 降为只判断非空。
- 不得只验证 status=ok 而不检查 evidence、action 和 final state。
- 不得只测试私有 helper 代替公开行为。
- 不得使用真实密钥或真实外部服务作为离线验收前提。

## 10. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 强类型迁移破坏 feedback/voice/checkpoint | G0 先建立外部和跨模块兼容测试；G1 提供单向读取适配；G7 再删除旧类型 |
| 中文语义 verifier 误判 | 普通 claim 使用混合 verifier；参数和安全 claim 使用规则硬门控；不确定时 fail closed |
| 模型主链导致离线测试不稳定 | 测试默认 MockModelClient；真实 Provider 不作为阶段验收条件 |
| RETRIEVE_MORE 无限循环 | typed directive、计划/证据指纹、独立 round 上限和无变化停止 |
| Prompt 或 trace 泄露隐私 | 只注入脱敏 memory 摘要；trace 只记录元数据和长度 |
| 清理误删设计能力 | 区分立即删除、迁移后删除和必须接线三类；删除前执行引用与契约审计 |
| 跨阶段重构违反 harness | G 工作包映射原 P 阶段，按 P0→P8 顺序拆提交并逐包更新 STATUS |
| 共享工作区覆盖用户变更 | 实施时使用独立 worktree；只提交本专项文件；提交前检查 git diff |

## 11. 回滚与停止条件

### 11.1 回滚规则

- 每个 G 工作包独立提交。
- 目标测试、前序回归或兼容测试失败时，不得进入下一工作包。
- 外部 JSON、CLI 或枚举破坏时，优先恢复边缘兼容适配，不保留双重内部实现。
- Prompt 版本质量下降时回滚 active version，不删除历史版本。
- 模型主路径不稳定时允许回滚到上一已验收版本，但 fallback 必须继续有清晰 trace。

### 11.2 强制停止条件

出现以下任一情况必须停止并记录到 `STATUS.md`：

1. 同一测试连续三次失败且无法定位根因。
2. 需要改变已批准的外部兼容边界。
3. 项目总控文档之间出现无法通过追加说明消解的冲突。
4. 需要新增大型依赖或编排框架，但现有 harness 未允许。
5. 需要访问真实密钥、真实生产数据库或真实外部服务。
6. 需要修改核心目录结构、安全边界或事实来源规则。
7. 当前实现会破坏现有接口契约或历史数据读取。
8. 清理项无法证明无仓库外兼容用途。

## 13. 专项完成定义

只有同时满足以下条件，才可声明回答生成专项完成：

- 外部请求、响应、CLI 和既有 trace 字段保持兼容。
- 模型主链在配置启用时真实执行，规则生成仅作为显式 fallback。
- 六类路由、澄清、参数、比较和安全行为符合设计。
- EvidenceSketch、AnswerPlan 和 AnswerOutline 均真实参与生成。
- 正文事实 claim 完整，空 claims 不能绕过 P5。
- 来源支持状态包含语义、对象、限定条件、证据类型、审核状态和权威等级判断。
- 安全步骤不能进入可发布正文。
- RETRIEVE_MORE 能改变检索目标并避免空转。
- REWRITE_ONLY 不残留 unsupported 正文。
- visual/source/display/spoken 输出均为已验证 envelope 的投影。
- generation、自检、安全和 fallback 各只有一条正式实现路径。
- 专项范围内不存在无引用接口、死代码、重复配置或未消费配置。
- 全量测试、离线评测、trace、compile 和 deployment validation 全部通过。
- 项目总控、接口、评测和 STATUS 文档与最终实现一致。
