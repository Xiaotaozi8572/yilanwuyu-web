# 翼览无余 Agent 后端接入文档（供 Unity / Pico 4 客户端负责人）

> 版本：v1.0（2026-08-16）
> 文档性质：后端（Python 仓库 `挑战杯`）对外接口的权威交付说明，面向 Unity / Pico 4 客户端接入负责人。
> 本文件只描述**后端提供什么、需要什么、还缺什么**，不修改任何代码；后端待补齐/待拍板事项集中在第 8 章。

## 1. 后端对外入口总览

后端刻意采用 CLI-first 策略，**没有 FastAPI/REST 服务**（见 `docs/接口与部署/api_contracts.md`）。当前对客户端暴露的入口共三个，其中只有第一个能被 Unity 直接对接：

| 入口 | 类型 | 当前形态 | 对 Unity 的可用性 |
| --- | --- | --- | --- |
| 语音实时服务 | WebSocket | `scripts/run_voice.py` 启动，`ws://127.0.0.1:<随机端口>/` | ✅ 唯一可对接的网络入口（含 ASR→问答→TTS 全闭环） |
| 文本问答 | CLI | `python -m app.cli --query "..."`，stdout 输出单个 JSON | ❌ 无网络入口，Unity 不可直接调用（见第 3、8 章） |
| 语音前端静态页 | HTTP（stdlib） | `scripts/run_frontend.py`，`http://127.0.0.1:8000/` | ❌ 仅演示用静态页，无 API 路由，与 Unity 无关 |

**结论：Unity 端当前唯一可对接的是语音 WebSocket 服务；协议细节见第 2 章。**

## 2. 语音 WebSocket 协议（P7 实时语音）

实现位置：`src/voice/websocket_server.py`（`serve_voice`）；启动脚本：`scripts/run_voice.py`；参考客户端：`src/voice/mock_client.py`、浏览器参考实现 `assets/voice/`；契约文档：`docs/接口与部署/api_contracts.md` §"P7 WebSocket 语音 Mock 协议"。

### 2.1 传输层

| 项 | 值 | 出处 |
| --- | --- | --- |
| 协议 | `ws://`（无 TLS、无鉴权、无子协议、`compression=none`） | `websocket_server.py:910-912` |
| 单条 wire 消息上限 | 128 KiB，超过由 websockets 在传输层以 `1009` 拒绝 | `websocket_server.py:28,910` |
| 控制帧（JSON 文本帧）上限 | 32 KiB；JSON 嵌套深度 ≤ 8 | `websocket_server.py:27,275,285` |
| 音频 binary 帧上限 | 非空且 ≤ 64 KiB（`MAX_AUDIO_FRAME_BYTES`） | `voice/transport.py:12`、`websocket_server.py:417` |
| 空闲超时 | 服务端对**单条消息**等待 30 秒；超时发送 `voice.error(VOICE_SESSION_TIMEOUT)` 并以 `4408` 关闭 | `websocket_server.py:230-236,618-638` |
| 绑定 | **当前硬编码仅允许 `127.0.0.1`/`localhost`/`::1`，且启动端口为随机（port=0）** | `websocket_server.py:878-879`、`scripts/run_voice.py:17` |

**实测提醒（2026-08-16 验证）**：客户端发送 WebSocket 协议级 ping，服务端会自动回 pong，但**应用层收不到、也不会重置 30 秒空闲计时**——ping 不能用作保活。保活必须用应用层帧，或采用 2.2 推荐的“按轮短连接”模式。

### 2.2 连接与绑定模型（Unity 端必须维护的状态）

**三个绑定 ID：`session_id` + `turn_id` + `audio_stream_id`（可选 `user_id`）。** 由客户端自行生成并保持每帧一致，规则（`websocket_server.py:29`）：

- 长度 1–128 字符，正则 `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`（**首字符必须是字母或数字**；`.` `_` `:` `-` 只允许出现在首字符之后）。

绑定与生命周期规则：

1. **首帧必须是 `session.start`**；同一连接只能 start 一次。违反 → `4400`。
2. 绑定后，后续每一帧都必须携带且**精确匹配**三个 ID，否则 `4401` 关闭，不会进入业务链（`websocket_server.py:709-724`）。
3. `session_id` 在同一服务实例内**单连接独占**；另一连接重复绑定 → `4401`，且不影响已有 owner（`websocket_server.py:61-87`）。
4. **多轮会话**：每轮（一次提问 → 回答 → 播报）建议**新建一条连接**，沿用同一 `session_id`，换新的 `turn_id`/`audio_stream_id`（官方集成测试模式：`tests/integration/voice_loop/test_disconnect_reconnect.py`、`test_clarify_continue_session.py`）。异常断开后服务端会强制重置该 turn，`session_id` 可复用（`websocket_server.py:640-675`）。
5. **推荐连接模式：激活式短连接**（按键说话 / 注视触发时建连，一轮结束后关闭）。理由：单连接 30 秒无消息即超时，且协议没有专用心跳帧，长驻连接保活不可靠。
6. 正常结束用关闭码 `1000`；服务端会正常收尾该轮（`finish_turn`），复用 session_id 无障碍。

### 2.3 上行控制帧（客户端 → 服务器，共 5 种）

严格 schema：**未知字段、缺失字段、类型错误一律 `voice.error(VOICE_PROTOCOL_INVALID)` + `4400` 关闭**（`websocket_server.py:747-762`）。`audio.frame` 采用二步成帧：先发 JSON 头，**紧随其后恰好一条** binary PCM 帧（详见 2.3 表后说明）。

| `type` | 必填字段 | 可选字段 | 校验要点 | 语义 |
| --- | --- | --- | --- | --- |
| `session.start` | `type`, `session_id`, `turn_id`, `audio_stream_id` | `user_id` | 三个 ID 均须符合 ID 规则；`user_id` 若给也须符合同一规则 | 绑定连接与 orchestrator session；**必须为该连接首帧** |
| `scene.update` | `type`, 三个 ID, `scene_state` | 无 | `scene_state` 只能是 dict 且键集 ⊆ SceneState 字段集（下表） | 声明/更新场景状态，用于指代绑定；收到后回 `voice.state(scene.updated)` |
| `audio.frame` | `type`, 三个 ID, `sequence`, `sample_rate`, `channels`, `timestamp_ms`, `energy` | 无 | `sequence` 首帧必须为 0、此后严格 +1（跳号/重复/倒退 → 4400）；`sample_rate`/`channels`/`timestamp_ms` 为 ≥0 整数（bool 除外）；`energy` 为数值 0.0–1.0（bool 除外） | 声明紧随其后的一条 PCM binary 帧元数据 |
| `audio.end` | `type`, 三个 ID | 无 | 只能发一次，其后不再接受 `audio.frame` | 关闭客户端 PCM 输入（服务端 VAD 端点由能量阈值判终，但客户端应主动发此帧） |
| `session.cancel` | `type`, 三个 ID | `feedback` | `feedback` 非空字符串 ≤ 256 字符，缺省为“停止” | barge-in 打断：停止当前播报，feedback 进入 P6 反馈改写链路 |

**二步成帧规则**（`docs/接口与部署/api_contracts.md:75-78`、`websocket_server.py:368-442`）：
- 每个 `audio.frame` JSON 头之后必须**恰好紧跟一条** binary 帧（无头 binary / 双头 / 双 binary / 头后接 JSON 均以 `4400` 拒绝）；
- binary 载荷为 **16-bit little-endian PCM 原始字节**，非空且 ≤ 64 KiB；
- `sequence` 从 0 起严格连续 +1。

**`scene_state` 允许字段**（对齐 `src/core/contracts.py:12-21` `SceneState`，校验在 `websocket_server.py:786-821`）：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `scene_state_id` | string/null | 符合 ID 规则（首字符字母数字、1–128 字符） |
| `aircraft_id` / `component_id` / `hotspot_label` / `camera_view` / `selected_object_id` | string/null | ≤ 128 字符 |
| `visual_refs` / `candidate_object_ids` | list/null | ≤ 128 项，每项 string ≤ 128 字符 |
| `scene_confidence` | number/null | 0.0–1.0 |

### 2.4 下行事件（服务器 → 客户端，JSON 文本帧）

| 事件 `type` | 字段 | 说明 |
| --- | --- | --- |
| `voice.state` | `session_id`, `turn_id`, `state`, `status` | `state` ∈ `IDLE / LISTENING / TRANSCRIBING / UNDERSTANDING / RETRIEVING / GENERATING / SPEAKING / INTERRUPTED / REWRITE / CLARIFY`（`src/voice/session_state.py:35-45`）；`status` ∈ `session.started` / `scene.updated` / `audio.input_ended` / `frame_accepted` / `partial` / `pre_retrieval` / `clarification` / `answered` / `barge_in.accepted` / `barge_in.cancelled` / `playback.failed` / `playback.completed` |
| `asr.partial` / `asr.final` | `session_id`, `turn_id`, `transcript`, `confidence`, `provider` | 仅回发当前连接的转写结果；`partial` 不是正式 RAG 事实来源；**只有 `asr.final` 才进入正式问答链路** |
| `clarification.required` | `session_id`, `turn_id`, `reason` | 低置信、指代不明或其他安全门控拒绝时发送；收到后客户端应提示用户重说/明确对象（**同连接继续说话**，无需重连） |
| `answer.display` | `session_id`, `turn_id`, `answer_id`, `evidence_package_id`, `answer` | 只来自已完成 P5 自检的可信 `TextQueryResponse`；**不含 prompt 与 trace**；`answer` 为 `AnswerEnvelope` 公共字典（结构见 2.6） |
| `barge_in.accepted` | `session_id`, `turn_id`, `status`, `intent` | 打断受理确认；`intent` ∈ `SIMPLIFY / SHORTEN / EXPAND / FORMAT_TRANSFORM / FACT_CHALLENGE / SCENE_REBIND / PREFERENCE_SIGNAL / SAFETY_SENSITIVE / STOP / CLARIFY`（`src/feedback/feedback_event.py:9-17`）。改写意图的新一代音频在该事件之后推送 |
| `voice.error` | `code`, `field` | **只含稳定机器码与字段名**，绝不回显原始音频 / transcript / prompt / 异常原文（隐私硬约束） |

### 2.5 下行 binary 帧（TTS 音频）

- `answer.display` 之后，服务器推送 **opaque MP3 二进制帧**（edge-tts 生成，`zh-CN-XiaoxiaoNeural`；每个口述段一个**完整 MP3 blob**，不是流式切片）（`src/voice/edge_tts.py:29,130-139`）。
- JSON 事件与 TTS binary 共用同一发送锁，**顺序有保证**（`websocket_server.py:90-109`）。
- TTS setup/stream 失败：**不会重跑 RAG**；客户端保留 `answer.display` 文本回答，随后收到 `voice.error(code)` + `voice.state(status="playback.failed")`。
- 口述回答上限：20 秒 / 180 字（`configs/voice.yaml`）。

### 2.6 `answer.display` 中的 `AnswerEnvelope` 公共字典

字段契约（`src/core/answer_contracts.py:842-864` `to_public_dict`）：

| 字段 | 说明 |
| --- | --- |
| `answer_id` | 回答 ID |
| `answer_type` | `concept_explanation / component_scene / comparison / parameter_fact / operation_safety / clarification`（`answer_contracts.py:11-17`） |
| `short_answer` / `main_answer` | 短答 / 正文 |
| `evidence_refs` | 证据引用列表（evidence_id） |
| `source_binding` | `{claim_id: [evidence_id, ...]}` 声明级来源绑定 |
| `visual_refs` | 视觉引用（3D 场景可据此高亮） |
| `uncertainty_notes` / `safety_notes` | 不确定说明 / 安全提示 |
| `follow_up_questions` | 追问建议 |
| `claim_candidates` | 每条含 `claim_id/text/claim_type/risk_level/required_evidence_type/minimum_authority/evidence_ids/source_origin/subject_refs/qualifiers/numeric_assertions`（可另含 `support_status`） |
| `display_blocks` | 展示块列表，`{type: "<kind>_block", text, claim_ids, evidence_refs, payload}`（可另含 `items/component_id/scene_object_id`） |
| `generation_trace` | 生成元数据（含 `model_provider`，不含 provider 内部细节） |

### 2.7 一轮典型时序（Unity 侧参考状态机）

```text
connect ──▶ session.start ──▶ voice.state(session.started)
   │              │
   │              └─▶ scene.update ──▶ voice.state(scene.updated)   [可选，推荐每轮都发]
   │
   ├─▶ audio.frame(seq=0) + binary PCM ──▶ voice.state(frame_accepted) [+ asr.partial …]
   ├─▶ …（连续流式，sequence 严格递增；能量低于阈值进入静音计数）
   ├─▶ audio.end ──▶ voice.state(audio.input_ended)
   │
   ├─▶ voice.state(TRANSCRIBING/UNDERSTANDING/RETRIEVING/GENERATING …)
   ├─▶ asr.final ──▶ … ──▶ answer.display ──▶ TTS MP3 binary × N（期间 voice.state(SPEAKING)）
   ├─▶ voice.state(playback.completed)          ── 或 ──▶ voice.error + playback.failed
   │
   └─▶ close(1000)  [本轮结束；下一轮新连接、同 session_id、新 turn_id]

任何时刻：session.cancel ──▶ barge_in.accepted ──▶ [改写后新 answer.display + 新音频]
任何时刻：clarification.required ──▶ 同连接继续说话（不发新 session.start）
```

## 3. 文本问答能力（当前仅 CLI，无网络入口）

Unity 如需**键盘/文字输入**问答，后端当前**没有可对接的网络接口**（只有 CLI，见 `src/app/cli.py`）。若决定补 HTTP 包装，可直接复用以下已有 schema（`src/app/api/schemas.py`、`src/app/api/errors.py`）：

**TextQueryRequest**：`query`(必填 string)、`scene_state`(dict/null)、`user_id`(string/null)、`session_id`(string/null)、`run_id`(string/null)、`turn_id`(string/null)、`source`(`"text"|"voice"`)。

**TextQueryResponse**：`run_id`、`status`(`ok|error`)、`answer`(AnswerEnvelope/null)、`action_decision`(`PASS/ASK_CLARIFICATION/STOP/...`)、`trace`、`error`(null 或 `{error_code, message, run_id}`)、`final_answer_id`、`evidence_package_id`、`check_report_id`、`self_check_completed`、`feedback_checkpoint_id`。

**错误码**：`invalid_request`、`pipeline_execution_error`（`src/app/api/errors.py:27-34`）。

> 此为**待决策项 D6**（第 8 章）：文本通道属后端新增接口，需要用户授权后才能开发。

## 4. 异常处理与错误码（Unity 端处理指南）

### 4.1 WebSocket 关闭码

| 关闭码 | 含义 | Unity 端建议动作 |
| --- | --- | --- |
| `1000` | 客户端正常结束 | 常规收尾，可复用 session_id 开新轮 |
| `4400` | 协议/schema 错误 | 客户端实现 bug（字段拼写、序列号跳号、超限、帧序错误等）——查日志与 4.2 的 `field` 定位，修复后重连 |
| `4401` | 绑定冲突 | session_id 被其他连接占用，或后续帧三个 ID 与 start 不一致——检查 ID 生成与一致性 |
| `4408` | 空闲/会话超时 | 正常现象（30 秒无消息）。**必须**新建连接、沿用 session_id、换新 turn_id 后重试当前轮 |
| `1009` | wire 消息超过 128 KiB | 传输层拒绝：检查 JSON 控制帧 ≤ 32 KiB、单帧 PCM ≤ 64 KiB |

### 4.2 `voice.error` 稳定机器码（`src/voice/errors.py:104-171`）

`VOICE_PROTOCOL_INVALID` / `VOICE_PROTOCOL_BINDING_MISMATCH` / `VOICE_SESSION_TIMEOUT` / `VOICE_TTS_ERROR` / `VOICE_TRANSPORT_ERROR` / `VOICE_ASR_ERROR` / `VOICE_STATE_INVALID` / `VOICE_CANCELLATION_FAILED` / `VOICE_PROCESSING_FAILED` / `VOICE_CONFIG_INVALID` / `VOICE_PROVIDER_ERROR` / `VOICE_ENDPOINT_ERROR` / `VOICE_CONTRACT_INVALID`。

> 错误事件**只含 `code` + `field`**，不回显任何 payload / transcript / prompt / 音频 / 异常原文。Unity 端 UI 不要展示 `field` 原文给用户，翻译成友好提示即可。

### 4.3 Unity 端通用异常策略（建议）

1. **断线重连**：任何非 `1000` 断开 → 复用 `session_id`、生成新 `turn_id`/`audio_stream_id` → 重连（服务端已保证异常断开后 session 可复用，`websocket_server.py:640-675`）。
2. **重试上限与退避**：连续失败 ≤ 3 次，指数退避（1s/2s/4s），超过后提示用户并复位会话。
3. **幂等**：每条消息有唯一 `sequence`/ID；重连后从 `session.start` 重新开始，**不要**重放旧连接的 `audio.frame`。
4. **降级**：`VOICE_TTS_ERROR`/`playback.failed` 时保留并显示 `answer.display` 文本（服务端保证不重跑 RAG）；`clarification.required` 时提示用户重说；`VOICE_ASR_ERROR`/`VOICE_PROCESSING_FAILED` 时提示“没听清，请再说一次”。
5. **用户状态管理**：维护 `session_id`（长生命周期）与 `turn_id`（每轮新）两个字段即可；`audio_stream_id` 每轮新。`session_id` 建议用 GUID（符合 ID 规则：首字符字母数字，仅字母数字和 `. _ : -`）。

## 5. 音频格式规格（Unity 采集/播放侧需要满足的输入输出）

### 5.1 上行（麦克风 → 后端）

| 参数 | 值 | 出处 |
| --- | --- | --- |
| 采样率 | 16000 Hz | `configs/voice.yaml` |
| 声道 | 1（单声道） | 同上 |
| 编码 | 16-bit little-endian PCM | `docs/接口与部署/api_contracts.md` |
| 帧长 | 20 ms = 640 字节/帧 | `configs/voice.yaml` `frame_duration_ms: 20` |
| `energy` | 客户端按帧自算，0.0–1.0；后端 VAD 阈值 0.2 | `voice.yaml` `vad_threshold: 0.2` |

- Pico 4 采集原始音频若为 48k/双声道，**Unity 侧需重采样到 16k 单声道**（后端不做重采样）。
- 服务端端点检测：能量 < 0.2 持续 600 ms 判终（`endpoint_silence_ms: 600`）；ASR 置信度 < 0.40 会触发澄清（`asr_low_confidence_threshold: 0.40`），不强答。

### 5.2 下行（后端 → 扬声器）

- 格式：**MP3**（完整 blob 每段一个）。Unity 运行时**没有内置的 MP3 流式解码**，需要 Unity 负责人确认解码方案（见第 8 章 D5）。
- 打断：用户在播报中说话/按键时，Unity 应立即发 `session.cancel`（优先级最高，`barge_in_priority: 100`）并停止本地播放。

   - 多轮/重连/打断的权威行为：`tests/integration/voice_loop/test_disconnect_reconnect.py`、`test_clarify_continue_session.py`；
4. 错误码表、关闭码表、音频参数表（本文第 4、5 章）。

### 7.2 必须补齐 / 待拍板（决策项）

| 编号 | 问题 | 现状与影响 | 可选方案 | 是否需要后端改代码 |
| --- | --- | --- | --- | --- |
| **D1** | **网络可达性：Pico 4 是独立头显，无法访问 PC 的 `127.0.0.1`** | `serve_voice` 硬编码拒绝非 loopback 绑定（`websocket_server.py:878-879`），`run_voice.py` 固定 `127.0.0.1` + 随机端口 | ① 后端放开 LAN 绑定（改 host 校验 + 打印局域网 IP）；② USB 线连 PC 时用 `adb reverse tcp:<port> tcp:<port>` 把流量反向转发（**零后端改动**，但需固定端口）；③ 后端部署到与头显同网段机器 | 方案①需改（**需用户授权**）；②③不改 |
| **D2** | 端口随机（`port=0`） | Unity 配置与 adb reverse 都需要**固定端口** | `run_voice.py` 增加 `--host/--port` 参数（改动小，但属接口变更） | 需改（**需用户授权**） |
| **D3** | 协议统一：`docs/unity-integration/unity-scripts/` 内 4 个 C# 参考脚本（`MessageEnvelope`/`agent.*` 信封协议）与本文语音帧协议**不一致** | 参考脚本无法直接对接现有后端 | ① Unity 按本文第 2 章重写参考脚本（**推荐**：后端零改动，后端唯一真实存在的线上能力就是语音帧协议）；② 后端新增 MessageEnvelope 网关适配层 | 方案②需改（**需用户授权 + 新增接口**） |
| **D4** | 无鉴权 | 一旦放开 LAN 绑定，局域网内任何设备可连 | ① 实验室环境接受无鉴权（演示/答辩场景）；② 增加静态 token（协议扩展或 URL 参数） | 方案②需改（**需用户授权**） |
| **D5** | TTS 下行是 MP3，Unity 无内置运行时 MP3 流式解码 | 播报功能取决于解码方案 | ① Unity 侧引入 MP3 解码（第三方库或 Pico 系统解码器）；② 后端转码为 WAV/PCM（需 ffmpeg 系统工具或新增 Python 依赖） | 方案②需改（**需用户授权**） |
| **D6** | 文本问答无网络入口 | Unity 若需要键盘输入/文字问答则无法对接 | ① 仅语音交互（当前能力范围）；② 后端新增 HTTP REST 包装（复用 TextQueryRequest/Response schema） | 方案②需改（**需用户授权 + 新增接口**） |
| **D7** | 协议无心跳帧，30 秒空闲超时不可由 ping 规避 | 长驻连接不可行 | 采用**按轮短连接**模式（第 2.2 条，推荐，无需改协议）；或后端增加心跳帧类型 | 后者需改（**需用户授权**） |

> 所有“需改代码”项都涉及 harness 白名单外的后端改动（R0 审阅修复专项逐任务白名单外文件一律不得修改），**必须先经用户明确授权**，再排入后端任务。

## 附录 B：与既有 Unity 参考脚本的差异说明（对应 D3）

`docs/unity-integration/unity-scripts/` 下 4 个 C# 文件为历史草稿（信封协议），与后端现行协议的关系：

| 文件 | 可复用性 | 说明 |
| --- | --- | --- |
| `MessageEnvelope.cs` | ⚠️ 需重写 | `msg_id/trace_id/agent.*` 信封与语音帧协议不兼容；但“协议版本字段 + 结构化消息”思路可保留 |
| `MessageCodec.cs` | ✅ 基本可复用 | JSON 编解码（Newtonsoft）+ UTF8 字节转换，改动很小（编码对象换成语音帧字典） |
| `MessageDispatcher.cs` | ✅ 基本可复用 | 事件路由/订阅器与协议无关，可直接复用 |
| `WsClient.cs` | ✅ 基本可复用 | NativeWebSocket 封装可复用；需补充 binary 帧发送（PCM 上行）与 binary 接收（MP3 下行）分支——当前 `OnMessage` 只处理文本 |
